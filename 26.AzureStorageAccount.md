# Azure Storage Account interview questions


## Part 1: Basic to Intermediate Level

### 1. What is an Azure Storage Account and what are its core components?
**Answer:**
An Azure Storage Account is a container that groups all of your Azure Storage data services together. It provides a unique namespace for your storage resources that is accessible from anywhere over HTTP or HTTPS .

**Core components (data services) within a storage account :**
- **Blob Storage:** For storing unstructured data like images, videos, and documents.
- **File Storage:** Fully managed file shares accessible via SMB or NFS protocol .
- **Queue Storage:** For storing large numbers of messages that can be accessed from anywhere.
- **Table Storage:** A NoSQL key-value store for structured data.

### 2. What are the different types of storage accounts available in Azure?
**Answer:**
Azure provides several types of storage accounts optimized for different use cases :

| Account Type | Description | Recommended Use |
|--------------|-------------|------------------|
| **General-purpose v2 (GPv2)** | The most versatile type supporting all storage services (blob, file, queue, table) | General storage needs, most common choice |
| **General-purpose v1 (GPv1)** | Older type with fewer features, lower cost but less flexible | Legacy applications |
| **BlobStorage** | Optimized for blob data only | Storing unstructured data only |
| **FileStorage** | Specialized for Azure Files with performance tiers | High-performance file share workloads |
| **Premium** | SSD-based for low-latency workloads | High-demand applications requiring consistent performance |

**Important note:** You can create up to **250 storage accounts** per subscription .

### 3. What are the different types of blobs in Azure Blob Storage?
**Answer:**
Azure Blob Storage offers three types of blobs, each optimized for different access patterns :

**1. Block Blobs:**
- Designed for efficient storage and retrieval of large files (text, images, videos, backups)
- Consist of data blocks that can be uploaded concurrently
- Maximum size: **Up to 190.7 TB** (with 50,000 blocks, each up to 4000 MiB) 

**2. Page Blobs:**
- Optimized for random read/write operations
- Used as backing storage for Azure Virtual Machines (VHD files)
- Provide low-latency data access

**3. Append Blobs:**
- Optimized for append operations (adding data to the end)
- Ideal for logging scenarios where you continuously add new data
- Cannot modify existing content, only append

### 4. Explain data redundancy options in Azure Storage.
**Answer:**
Azure Storage offers several replication options to protect data against failures :

- **Locally Redundant Storage (LRS):** Copies data three times within a single data center in the primary region. Protects against server/drive failures but not datacenter failures.

- **Zone-Redundant Storage (ZRS):** Copies data synchronously across three Azure availability zones in the primary region. Protects against datacenter-level failures.

- **Geo-Redundant Storage (GRS):** Copies data three times locally (LRS) in the primary region, then asynchronously copies to a secondary region hundreds of miles away. Protects against regional disasters.

- **Geo-Zone-Redundant Storage (GZRS):** Combines ZRS in the primary region with geo-replication to a secondary region. Highest durability and availability.

### 5. What are access tiers in Azure Blob Storage?
**Answer:**
Azure Blob Storage offers access tiers to optimize costs based on how frequently data is accessed :

| Tier | Access Frequency | Storage Cost | Access Cost | Minimum Duration |
|------|-----------------|--------------|-------------|------------------|
| **Hot** | Frequently accessed (at least once a month) | Highest | Lowest | None |
| **Cool** | Infrequently accessed (less than once a month) | Lower | Higher | 30 days |
| **Cold** | Rarely accessed | Even lower | Even higher | 90 days |
| **Archive** | Long-term retention (less than once a year) | Lowest | Highest | 180 days |

**Moving between tiers:**
- You can move data manually or set up lifecycle management policies to automatically transition data between tiers based on age .

### 6. What happens when you transition data to the Archive tier?
**Answer:**
When you transition data to the Archive tier :
- The system moves data to the lowest-cost storage option designed for long-term retention
- Data is no longer immediately available for read or write operations
- To access archived data, you must **rehydrate** it by moving it back to Hot or Cool tier
- Rehydration can take several hours (depending on blob size and priority)
- During rehydration, the blob is read-only and cannot be modified or deleted
- Rehydration incurs additional costs, so it should be used infrequently 

### 7. What are the different ways to access a storage account in Azure?
**Answer:**
There are multiple ways to access Azure Storage :

1. **Storage Account Access Keys:** Two 512-bit keys generated by Azure (can be regenerated anytime)
2. **Azure Role-Based Access Control (RBAC):** Manage permissions to blob, queue, and table resources
3. **Azure AD Authentication:** Using managed identities or service principals
4. **Shared Access Signatures (SAS):** Time-limited, delegated access tokens
5. **Client Libraries:** .NET, Java, Python, Node.js, etc.
6. **REST API:** Direct HTTP/HTTPS access
7. **Storage Explorer:** GUI tool for managing storage
8. **Azure CLI/PowerShell:** Command-line management

### 8. Why does a storage account have two access keys?
**Answer:**
Azure provides two access keys to enable **key rotation without downtime** .

**Rotation process:**
1. Regenerate Key 2 (applications using Key 2 must be updated)
2. Update all applications to use Key 2
3. Regenerate Key 1
4. Update applications back to Key 1 (or continue with Key 2)

This ensures you always have a valid key while rotating credentials.

## Part 2: Intermediate to Advanced Level

### 9. What is the difference between Azure Blob Storage and ADLS Gen2?
**Answer:**
Azure Data Lake Storage Gen2 is built on top of Blob Storage but adds key differences :

| Feature | Azure Blob Storage | ADLS Gen2 |
|---------|-------------------|-----------|
| **Namespace** | Flat namespace (containers only) | Hierarchical namespace (directories/subdirectories) |
| **Performance** | Standard | Optimized for big data workloads |
| **Access Control** | Container-level RBAC | File/directory level ACLs (POSIX-compliant) |
| **Use Case** | General-purpose storage | Big data analytics, data lakes |

**When to choose Blob Storage:**
- Simple object storage
- Website content, backups, archives
- When hierarchical namespace isn't needed

**When to choose ADLS Gen2:**
- Big data workloads (Spark, Hadoop, etc.)
- Need for file/folder-level permissions
- High-performance analytics 

### 10. Explain Shared Access Signatures (SAS) and their types.
**Answer:**
A Shared Access Signature (SAS) is a time-limited, delegated URI that grants restricted access to storage resources .

**Types of SAS :**

1. **Service SAS:** Secures access to a specific resource (blob, container, file, queue, table)
2. **Account SAS:** Secures access to one or more storage services and also allows operations like GET Service Properties
3. **User Delegation SAS:** Secured with Azure AD credentials rather than account key

**Example scenario :**
> A partner needs temporary access to upload files to your Blob container for 24 hours.
> **Solution:** Generate a Service SAS with:
> - Write and List permissions
> - 24-hour expiry
> - HTTPS-only access
> - Optional IP restriction to their network range

### 11. Can you revoke a SAS token before it expires? If so, how?
**Answer:**
SAS tokens themselves **cannot be revoked once generated**—they remain valid until expiry . However, there are two ways to effectively revoke them :

1. **Use a Stored Access Policy:**
   - Create a stored access policy on the container
   - Generate SAS tokens linked to that policy
   - To revoke: delete or modify the stored access policy—all SAS tokens linked to it are immediately invalidated

2. **Regenerate the Storage Account Key:**
   - This immediately invalidates all SAS tokens signed with that key
   - Warning: This affects all applications using that key

### 12. How do you provide access to a storage account for an Azure VM without using connection strings or keys?
**Answer:**
Enable **Managed Identity** for the VM and use Azure RBAC :

**Steps:**
1. Enable system-assigned or user-assigned managed identity on the VM
2. Assign the appropriate RBAC role (e.g., **Storage Blob Data Contributor**) to that identity
3. Scope the role assignment to the specific container or storage account

**Benefits :**
- No connection strings or keys to manage
- VM authenticates to Azure AD and obtains OAuth token
- Fine-grained access control with least privilege

### 13. What factors affect the cost of a storage account?
**Answer:**
Several factors influence storage account costs :

1. **Storage capacity:** Amount of data stored (GB/month)
2. **Access tier:** Hot, Cool, Cold, or Archive (different base storage costs)
3. **Data transfer:** Ingress (free), egress (charged)
4. **Transaction count:** Number of read/write/list operations
5. **Geo-replication:** LRS, ZRS, GRS, GZRS (increasing cost with durability)
6. **Region:** Prices vary by geographic region 
7. **Redundancy:** Higher redundancy = higher cost

**Cost optimization tip:** Choose the lowest-cost region that meets latency requirements, not necessarily the cheapest region .

### 14. What is Azure Files and when would you use it?
**Answer:**
Azure Files is a fully managed cloud file share service accessible via **SMB (Server Message Block)** or **NFS (Network File System)** protocol .

**Use cases :**
- Replacing or supplementing on-premises NAS devices or file servers
- **Lift-and-shift** applications that need a file share for application data
- Sharing application settings across multiple instances
- Storing application diagnostics (logs, metrics, crash dumps)

**Connection requirements:**
- SMB access requires **TCP port 445** outbound from the client 
- UNC path format: `\\<storage-account>.file.core.windows.net\<share-name>` 
- Credentials format: `AZURE\<storage-account-name>` with account key as password 

### 15. If port 445 is blocked on your corporate network, how can you still access Azure Files?
**Answer:**
If outbound TCP 445 is blocked (common in corporate networks), you have options :

1. **VPN/ExpressRoute:** Establish a private connection so traffic uses a private path where port restrictions don't apply
2. **Private Endpoints:** Configure private endpoints for Azure Files, placing the file share on your VNet with a private IP 
3. **REST API access:** Use Azure Files REST API over HTTPS (port 443) instead of SMB

### 16. What is Azure File Sync and how does it work?
**Answer:**
Azure File Sync centralizes file shares in Azure while keeping the flexibility, performance, and compatibility of Windows Server .

**Key components :**
- **Storage Sync Service:** The Azure resource that manages sync relationships
- **Sync Group:** Defines sync relationship between one Cloud Endpoint and one or more Server Endpoints
- **Cloud Endpoint:** The Azure File Share that is linked to the sync group
- **Server Endpoint:** A path on a registered Windows Server that syncs with the cloud endpoint

**Requirements:**
- Install **Azure File Sync agent** on Windows Server and register it with Storage Sync Service 
- Windows Server only (Linux/macOS can mount Azure Files but cannot be sync endpoints) 

### 17. What is Cloud Tiering in Azure File Sync?
**Answer:**
Cloud Tiering is a feature that keeps frequently accessed files cached locally on the server while tiering older files to Azure Files .

**How it works :**
- Namespace (file and folder structure) remains visible locally
- File content is moved to Azure Files based on access patterns
- When a tiered file is accessed, it's recalled from Azure (requires network)

**Benefits:**
- Saves local disk space
- Keeps warm data accessible with low latency
- Cold data stored cost-effectively in Azure

### 18. What is the difference between Service Endpoints and Private Endpoints?
**Answer:**
Both secure access to Azure Storage but work differently :

| Feature | Service Endpoint | Private Endpoint |
|---------|------------------|------------------|
| **Traffic path** | Uses Azure backbone but still reaches public endpoint | Maps service to private IP in your VNet |
| **IP addressing** | Public IP (with subnet restriction) | Private IP from your VNet |
| **Network isolation** | Traffic stays on Azure network | Service is effectively "in" your VNet |
| **DNS resolution** | Resolves to public IP | Resolves to private IP |
| **Cost** | Free | Incurs hourly charge |
| **On-premises access** | Not directly (unless VPN) | Yes (via VPN/ExpressRoute) |

**Choose Service Endpoint when:** You need to restrict access to specific subnets and don't need private IPs .

**Choose Private Endpoint when:** You need to access storage from on-premises privately, or want the service to have an IP from your VNet .

### 19. You created a private endpoint but clients still resolve to public IP. What's wrong?
**Answer:**
The most likely missing step is **DNS configuration** .

**Issue:**
Without proper DNS configuration, the storage account name continues resolving to the public IP even though a private endpoint exists.

**Solution :**
- Ensure the Private DNS zone is linked to the VNet
- The private endpoint should create/use a `privatelink.blob.core.windows.net` DNS zone
- Configure on-premises DNS to forward to Azure or resolve the privatelink zone

### 20. How would you restrict access to a storage account so only a specific subnet can access it, without using private IPs?
**Answer:**
Use **Service Endpoint + Storage Firewall** :

**Configuration:**
1. Enable service endpoint for `Microsoft.Storage` on the specific subnet
2. Configure storage account firewall to "Selected networks"
3. Add the virtual network/subnet to the allowed list

**Why this works :**
- Service endpoints keep traffic on Azure backbone
- Firewall restricts access to only the specified subnet
- No private IPs required (still uses public endpoint)

### 21. A user wants to ensure files aren't lost even if someone deletes them. What would you recommend?
**Answer:**
Implement multiple data protection mechanisms :

1. **Soft Delete:**
   - Enabled at storage account level
   - Retains deleted blobs for a configurable period
   - Allows undelete operations

2. **Snapshots:**
   - Point-in-time read-only copies of blobs 
   - Can restore to previous versions

3. **Azure Backup:**
   - Configure backup for Azure File Shares
   - Centralized management and recovery

4. **Immutable Storage:**
   - WORM (Write Once, Read Many) policy
   - Legal hold or time-based retention
   - Prevents modification/deletion even by administrators

5. **RBAC with least privilege:**
   - Don't give delete permissions to all users
   - Use roles like "Storage Blob Data Reader" for read-only access

### 22. How would you design a solution for a website where users upload PDF/images, and these need to be accessible for a limited time?
**Answer:**
Combine multiple Azure Storage features :

**Solution design:**
1. **Storage:** Blob Storage with Hot tier for active uploads
2. **Access:** Use container-level RBAC for internal users, SAS tokens for external
3. **Expiration:** Configure SAS tokens with specific expiry times 
4. **Lifecycle management:** Move older files to Cool/Archive tier after threshold
5. **Cleanup:** Use lifecycle policies to delete files after retention period

**Example:**
- Upload container: Private (internal uploads only)
- Generate SAS URLs for each uploaded file with 24-hour expiry
- Share SAS URLs with intended recipients
- Access automatically expires after 24 hours 

### 23. How do you monitor and troubleshoot storage account performance and costs?
**Answer:**
Use Azure monitoring tools :

**For cost monitoring:**
- **Azure Cost Management + Billing:** Track spending by storage account
- **Storage Insights:** Azure Monitor workbook for storage
- **Metrics:** Track used capacity, transaction counts

**For performance troubleshooting:**
- **Azure Monitor metrics:**
  - Success E2E Latency, Success Server Latency
  - Transactions by API name
  - Ingress/Egress metrics
  - Throttling errors

- **Storage Analytics Logs:**
  - Detailed information about successful/failed requests
  - Helps identify slow queries or hot partitions

- **Diagnose and solve problems:**
  - Built-in troubleshooting blade in storage account
  - Guided scenarios for common issues

### 24. What happens if you reach the scalability limits of a storage account?
**Answer:**
Storage accounts have scalability targets :

| Resource | Limit (Standard) |
|----------|------------------|
| Storage accounts per subscription | 250 |
| Max ingress per storage account (US/Europe) | 25 Gbps |
| Max egress per storage account (US/Europe) | 50 Gbps |
| Max storage account capacity | 5 PiB |

**If you approach limits:**
1. **Monitor** metrics for throttling (ServerBusy errors)
2. **Scale out:** Create additional storage accounts and distribute data
3. **Use Premium storage** for higher IOPS/latency requirements
4. **Optimize application:** Reduce number of transactions, use caching

### 25. You're getting a 403 error when accessing blobs from an App Service. How do you troubleshoot?
**Answer:**
A 403 (Forbidden) error indicates authorization issues. Follow these steps :

**1. Check network access:**
- Verify the storage account firewall allows the App Service outbound IPs
- If using VNet integration, ensure service endpoints or private endpoints are configured

**2. Check authentication method:**
- If using access keys, verify they're correct and not expired
- If using SAS tokens, check if they've expired or permissions are correct
- If using RBAC, verify the identity has the correct role assigned

**3. For Managed Identity:**
- Verify managed identity is enabled on App Service
- Confirm RBAC role (e.g., "Storage Blob Data Contributor") is assigned to the identity
- Check that the identity has access at the correct scope (container vs account)

**4. Check shared key access:**
- Storage account setting "Allow shared key access" must be enabled if using keys
