## Basic Docker Image Questions

### Q1: What is a Docker image?

**Answer:**
A **Docker image** is a lightweight, standalone, and **read-only template** that contains everything needed to run an application—including the code, runtime, system tools, system libraries, and settings . It serves as a blueprint for creating Docker containers.

**Key characteristics**:
- **Read-only**: Images cannot be modified directly; changes create new layers
- **Portable**: Can be stored in registries and pulled to any Docker host
- **Immutable**: Once built, the image doesn't change
- **Layer-based**: Composed of multiple read-only layers

**Simple analogy**: An image is like a class in object-oriented programming (the blueprint), while a container is like an instance of that class (the running object).

### Q2: How is a Docker image different from a Docker container?

**Answer:**
This is one of the most fundamental concepts in Docker :

| Aspect | Docker Image | Docker Container |
|--------|--------------|------------------|
| **Nature** | Read-only template | Runnable instance of an image |
| **State** | Static, immutable | Dynamic, can be started/stopped/modified |
| **Layers** | Multiple read-only layers | Image layers + writable container layer |
| **Persistence** | Permanent (until deleted) | Ephemeral (data lost unless persisted) |
| **Creation** | Built via `docker build` | Created via `docker run` |
| **Sharing** | Stored/pushed to registries | Not shared directly |

**How to explain in an interview**:
"A Docker image is like a **blueprint** or a **recipe**—it defines what should be in your application environment. A Docker container is a **running instance** of that blueprint. You can create multiple containers from the same image, just like you can build multiple houses from the same blueprint" .

### Q3: What is a base image?

**Answer:**
A **base image** is the starting point for building your own Docker images, specified using the `FROM` instruction in a Dockerfile . It provides the foundation upon which you add your application code and dependencies.

**Examples**:
- `FROM ubuntu:22.04` - Ubuntu Linux base
- `FROM alpine:3.19` - Minimal Alpine Linux (≈5MB)
- `FROM node:18-alpine` - Node.js runtime on Alpine
- `FROM python:3.11-slim` - Python on slim Debian

**Base image vs. final image**:
- **Base image**: The initial layer (e.g., `ubuntu:22.04`)
- **Final image**: Base image + all your added layers (app code, dependencies, configs)

### Q4: What is a Dockerfile?

**Answer:**
A **Dockerfile** is a text document that contains all the commands a user could call on the command line to assemble an image . It provides a way to **automate the image creation process**, ensuring reproducibility and version control for your application's environment.

**Example Dockerfile**:
```dockerfile
FROM node:18-alpine        # Base image
WORKDIR /app               # Set working directory
COPY package*.json ./       # Copy dependency files
RUN npm install            # Install dependencies
COPY . .                   # Copy application code
EXPOSE 3000                # Document exposed port
CMD ["npm", "start"]       # Default command
```

### Q5: What is Docker Hub and how does it relate to images?

**Answer:**
**Docker Hub** is a cloud-based registry service provided by Docker for finding and sharing container images . It acts as a central repository where:

- You can **pull** official and community-contributed images (e.g., `nginx`, `mysql`, `ubuntu`)
- You can **push** your custom images to share with others or for backup
- Images are organized in repositories (e.g., `library/nginx`, `yourusername/myapp`)

**Key features**:
- Public and private repositories
- Official images for popular software
- Automated builds from GitHub/Bitbucket
- Webhooks for CI/CD integration

### Q6: What is an image tag and why is it important?

**Answer:**
An **image tag** is a label applied to an image to identify specific versions or variants . Tags make it possible to have multiple versions of the same image.

**Tag syntax**: `repository:tag` (e.g., `nginx:1.25`, `ubuntu:22.04`, `myapp:latest`)

**Important concepts**:
- **`latest` is just a tag**: It's a convention, not a special version. `ubuntu:latest` points to the most recent stable Ubuntu release.
- **Tags are mutable**: The same tag can point to different images over time.
- **Best practice**: Use specific version tags (`v1.2.3`) rather than `latest` for production deployments to ensure reproducibility .

**Tagging commands**:
```bash
# Tag during build
docker build -t myapp:1.0.0 .

# Tag existing image
docker tag myapp:1.0.0 myapp:latest
```

### Q7: What is the difference between an image name, tag, and digest?

**Answer:**
These three identifiers serve different purposes :

| Identifier | Format | Mutability | Use Case |
|------------|--------|------------|----------|
| **Name** | `repository:tag` (e.g., `nginx:latest`) | Mutable | Human-readable reference |
| **Tag** | Part of name (e.g., `1.25`, `latest`) | Mutable | Version/label |
| **Digest** | `sha256:abc123...` | Immutable | Guaranteed exact image |

**How to use digests**:
```bash
# Pull by digest (guarantees exact image)
docker pull nginx@sha256:abc123def456...

# Use in deployments (most reliable)
image: nginx@sha256:abc123def456...
```

**Why digests matter**: Unlike tags, which can change (someone might push a new image to `nginx:latest`), a digest always points to the exact same image content. This is crucial for security and reproducibility .

### Q8: How do you list Docker images on your system?

**Answer:**
Use the `docker images` command (or `docker image ls`) to list all images stored locally .

```bash
docker images

# Output:
REPOSITORY   TAG       IMAGE ID       CREATED       SIZE
nginx        latest    abc123def456   2 weeks ago   187MB
myapp        v1.0.0    def456ghi789   3 days ago    125MB
```

**Useful variations**:
```bash
# Show only image IDs
docker images -q

# Show with digests
docker images --digests

# Filter images
docker images --filter "dangling=true"  # Show untagged images
```

### Q9: How do you remove a Docker image?

**Answer:**
Use the `docker rmi` (remove image) command :

```bash
# Remove by tag
docker rmi myapp:1.0.0

# Remove by image ID
docker rmi abc123def456

# Remove multiple images
docker rmi image1:tag image2:tag

# Force remove (even if used by containers)
docker rmi -f image:tag
```

**Remove unused images**:
```bash
# Remove dangling images (untagged, not referenced)
docker image prune

# Remove all unused images
docker image prune -a
```

### Q10: What is a dangling image?

**Answer:**
A **dangling image** is an untagged image that is not referenced by any container . They typically occur when:

- Rebuilding an image with the same tag (the old image becomes untagged)
- Intermediate images from failed builds

**How to find dangling images**:
```bash
docker images --filter "dangling=true"
```

**Why clean them**: Dangling images waste disk space and can accumulate over time.

**How to remove**:
```bash
docker image prune
```

## Intermediate Docker Image Questions

### Q11: How are Docker images built from a Dockerfile?

**Answer:**
Docker builds images by executing each instruction in the Dockerfile sequentially, creating a new **read-only layer** for each instruction .

**Build process**:
1. **Context preparation**: Docker client sends build context (directory contents) to Docker daemon
2. **Layer creation**: Each instruction creates a new layer
3. **Caching**: Docker checks if each layer can be reused from cache
4. **Image assembly**: Layers are stacked to form the final image

**Build command**:
```bash
docker build -t myapp:1.0.0 .
```

**What happens during build**:
```
Step 1/5 : FROM node:18-alpine
 ---> abc123
Step 2/5 : WORKDIR /app
 ---> def456
Step 3/5 : COPY package*.json ./
 ---> ghi789
Step 4/5 : RUN npm install
 ---> jkl012
Step 5/5 : COPY . .
 ---> mno345
Successfully built mno345
Successfully tagged myapp:1.0.0
```

### Q12: What are image layers and how do they work?

**Answer:**
**Image layers** are the fundamental building blocks of Docker images . Each instruction in a Dockerfile creates a new read-only layer.

**Key characteristics**:
- **Stacked**: Layers are stacked on top of each other
- **Read-only**: Layers are immutable once created
- **Content-addressed**: Each layer is identified by a hash of its content
- **Shared**: Identical layers are shared across images, saving disk space and bandwidth

**Example of layers**:
```
Image: myapp:latest
+-------------------+  <-- Layer 5: COPY . . (app code)
+-------------------+
| Layer 4: RUN npm install |  (dependencies)
+-------------------+
| Layer 3: COPY package*.json |
+-------------------+
| Layer 2: WORKDIR /app |
+-------------------+
| Layer 1: FROM node:18-alpine |
+-------------------+
```

**How to view layers**:
```bash
docker history myapp:latest
```

### Q13: How does Docker's Union File System (OverlayFS) help image creation?

**Answer:**
Docker uses a **Union File System** (typically OverlayFS) to combine multiple read-only image layers with a writable container layer into a single unified filesystem view .

**How it works**:
- **Lower directories**: The read-only image layers
- **Upper directory**: The writable container layer (changes made in container)
- **Merged view**: The unified filesystem seen by the container

**Benefits**:
- **Efficient storage**: Only the writable layer is created per container
- **Fast assembly**: Layers are stacked, not copied
- **Memory efficiency**: Multiple containers can share the same base layers
- **Copy-on-Write (CoW)**: Files are only copied to the writable layer when modified

**Technical explanation**: "Docker uses overlay2 (UnionFS) to stack image layers and show a unified filesystem. It allows reusing read-only layers across containers and adds a writable layer for container-specific changes" .

### Q14: Explain the Copy-on-Write (CoW) concept in Docker

**Answer:**
**Copy-on-Write (CoW)** is a strategy used by Docker to optimize storage and memory usage . When a container tries to modify a file from a read-only image layer, Docker:

1. **Copies** the file from the read-only layer to the container's writable layer
2. **Modifies** the copy in the writable layer
3. **Preserves** the original file in the read-only layer

**Why it matters**:
- **Efficiency**: Multiple containers can share the same base image layers
- **Speed**: Files are only copied when actually modified
- **Isolation**: Changes in one container don't affect others

**Visual representation**:
```
Read-only layers: L1 (OS) -> L2 (libs) -> L3 (app)
Container modifies /app/config.yaml:
  -> File copied from L3 to writable layer
  -> Modified in writable layer
  -> Original remains unchanged in L3
```

### Q15: How does Docker build caching work?

**Answer:**
Docker **caches each layer** during the build process . When rebuilding an image, Docker checks if any instruction or its context has changed:

- **Cache hit**: If the instruction and input files haven't changed, Docker reuses the cached layer
- **Cache miss**: If changes are detected, Docker invalidates the cache for this and all subsequent layers

**Cache invalidation rules**:
- `FROM` layer: Cached if base image ID matches
- `RUN` layer: Cached if command string is identical
- `COPY`/`ADD` layers: Cached if file contents and metadata are identical
- After a cache miss, all subsequent layers are rebuilt

**Optimization strategies**:
```dockerfile
# BAD - cache invalidates on every code change
COPY . /app
RUN npm install

# GOOD - dependencies cached separately
COPY package*.json /app/
RUN npm install
COPY . /app/
```

**View build cache**:
```bash
docker builder prune -f  # Clean cache
docker system df          # View cache usage
```

### Q16: Why are smaller images better in production?

**Answer:**
Smaller Docker images provide multiple benefits in production environments :

| Benefit | Impact |
|---------|--------|
| **Faster deployments** | Smaller images pull faster, reducing deployment time |
| **Lower bandwidth** | Less data transferred from registry to nodes |
| **Less disk space** | More images can be stored on each node |
| **Smaller attack surface** | Fewer packages = fewer vulnerabilities |
| **Faster CI/CD** | Build, push, and scan operations complete quicker |

**Real-world impact**: In one case study, optimizing images reduced build times by over 50% and image sizes by 60-75%, cutting deployment times significantly .

### Q17: What is multi-stage builds and why use them?

**Answer:**
**Multi-stage builds** allow you to use multiple `FROM` statements in a single Dockerfile, each starting a new build stage . This enables you to:

1. Use a large image with build tools for compilation/testing
2. Copy only the final artifacts to a small runtime image
3. Exclude build dependencies from the final image

**Example for Java application**:
```dockerfile
# Build stage with full JDK
FROM maven:3.8-openjdk-17 AS builder
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn clean package

# Runtime stage with only JRE
FROM eclipse-temurin:17-jre-alpine
COPY --from=builder /app/target/*.jar /app/app.jar
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

**Example for Go application**:
```dockerfile
# Build stage
FROM golang:1.21 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o myapp

# Runtime stage (only 20MB instead of 800MB)
FROM alpine:latest
RUN apk --no-cache add ca-certificates
COPY --from=builder /app/myapp /usr/local/bin/
ENTRYPOINT ["/usr/local/bin/myapp"]
```

### Q18: What is the difference between COPY and ADD in a Dockerfile?

**Answer:**
Both instructions copy files into the image, but **ADD** has additional features that can be useful but also risky :

| Aspect | COPY | ADD |
|--------|------|-----|
| **Basic function** | Copies local files/directories to image | Copies files/directories to image |
| **URL support** | No | Can download from remote URLs |
| **Tarball extraction** | No | Automatically extracts local tar archives |
| **Best practice** | Preferred for simple file copying | Use only when you need extra features |

**Examples**:
```dockerfile
# COPY - simple, predictable
COPY ./app /app
COPY requirements.txt /tmp/

# ADD - can extract tarballs
ADD app.tar.gz /app/        # Automatically extracts
ADD https://example.com/file.tar.gz /tmp/  # Downloads from URL
```

**Interview tip**: "I prefer `COPY` for most cases because it's more transparent. I only use `ADD` when I specifically need automatic tar extraction or remote URL downloading" .

### Q19: What is the difference between ARG and ENV in a Dockerfile?

**Answer:**
Both are used for variables, but they serve different purposes and scopes :

| Aspect | ARG | ENV |
|--------|-----|-----|
| **Scope** | Build-time only | Build-time + runtime |
| **Persistence** | Not available in running container | Available in container environment |
| **Overriding** | `--build-arg` during build | Can be overridden at runtime (`-e`) |
| **Use case** | Build configuration (versions, flags) | Application configuration |

**Example**:
```dockerfile
# ARG - only during build
ARG NODE_VERSION=18
FROM node:${NODE_VERSION}-alpine

# ENV - available at runtime
ENV NODE_ENV=production
ENV PORT=3000

# ARG can be used to set ENV
ARG VERSION
ENV APP_VERSION=${VERSION}
```

**Build with ARG**:
```bash
docker build --build-arg NODE_VERSION=20 -t myapp .
```

### Q20: What is the difference between CMD and ENTRYPOINT?

**Answer:**
Both define what command runs when a container starts, but they behave differently :

| Aspect | CMD | ENTRYPOINT |
|--------|-----|------------|
| **Purpose** | Provides default arguments | Defines the executable |
| **Overridability** | Easily overridden by command-line | Harder to override (needs `--entrypoint`) |
| **Usage alone** | `CMD ["executable", "param1"]` | `ENTRYPOINT ["executable", "param1"]` |
| **Together** | Provides default args to ENTRYPOINT | Sets main command |

**Best practice pattern**:
```dockerfile
ENTRYPOINT ["nginx"]
CMD ["-g", "daemon off;"]
# Run: docker run myimage → nginx -g "daemon off;"
# Run: docker run myimage -g "error_log off;" → nginx -g "error_log off;"
```

**Common use cases**:
- **Fixed executable**: Use `ENTRYPOINT` for the main command
- **Default arguments**: Use `CMD` for parameters that users might override
- **Tool containers**: `ENTRYPOINT` for the tool, `CMD` for default action

## Advanced Docker Image Questions

### Q21: What is an image digest and why is it important for security?

**Answer:**
An **image digest** is a **content-based hash** (SHA256) that uniquely identifies an image . Unlike tags (which are mutable), digests are **immutable**—they always point to the exact same image content.

**Why digests matter for security**:
- **Immutability**: Guarantees you're pulling the exact image you expect
- **Prevents tag tampering**: Tags can be changed to point to malicious images
- **Auditability**: Provides cryptographic proof of image content
- **Reproducible deployments**: Same digest = same image, every time

**Using digests**:
```bash
# Pull by digest
docker pull nginx@sha256:abc123def456...

# Reference in Kubernetes
image: nginx@sha256:abc123def456...
```

**How to find digest**:
```bash
docker images --digests
docker inspect nginx:latest | grep RepoDigests
```

### Q22: How are layers shared between images and why does this matter?

**Answer:**
Docker identifies layers using **content-addressable digests** . If two images share the same layer (identical content), it's stored **only once** on disk and in the registry.

**How sharing works**:
```
Image A: [Layer1][Layer2][Layer3]
Image B: [Layer1][Layer4]
Layer1 is shared by both images
```

**Benefits**:
- **Disk space efficiency**: Common base layers stored once
- **Network efficiency**: During push/pull, shared layers aren't re-transferred
- **Memory efficiency**: Containers share base layers in memory
- **Faster deployments**: Nodes may already have common layers cached

**Real-world example**: If you have 10 images all based on `ubuntu:22.04`, the Ubuntu layers are stored once, saving gigabytes of disk space.

### Q23: What happens when you push an image to a registry?

**Answer:**
When pushing an image to a registry like Docker Hub, several steps occur :

1. **Authentication**: Docker authenticates with the registry
2. **Layer check**: Docker checks which layers already exist in the registry
3. **Layer upload**: Only **missing layers** are uploaded (blobs)
4. **Manifest creation**: A manifest is created that lists all layers
5. **Tag update**: The tag is updated to point to the new manifest

**Why this matters**:
- **Incremental pushes**: Only changed layers are uploaded
- **Efficient storage**: Shared layers across images aren't duplicated
- **Fast updates**: Small code changes mean fast pushes

**Visual process**:
```
docker push myapp:latest
  ├── Check registry for existing layers
  ├── Upload Layer 4 (new/changed)
  ├── Upload manifest referencing [Layer1,Layer2,Layer3,Layer4]
  └── Update tag "latest" to new manifest
```

### Q24: How do you inspect the contents of an image without running it?

**Answer:**
Multiple methods to examine image contents :

**Method 1: `docker history`** - Show layer information
```bash
docker history myapp:latest
```

**Method 2: `docker inspect`** - Detailed metadata
```bash
docker inspect myapp:latest
```

**Method 3: Create temporary container to explore**
```bash
# Create container without starting
docker create --name temp myapp:latest

# Export and extract filesystem
docker export temp | tar -tvf - | grep something

# Or use cp to extract specific files
docker cp temp:/app/config.yaml ./config.yaml

# Clean up
docker rm temp
```

**Method 4: Use `dive` tool** (third-party) for interactive inspection
```bash
dive myapp:latest
```

### Q25: How do you handle image versioning and release management?

**Answer:**
Image versioning should follow **semantic versioning (SemVer)** principles :

**Tagging strategy**:
```bash
# During development
myapp:1.2.3-beta.1
myapp:1.2.3-rc.1

# Release versions
myapp:1.2.3          # Specific version
myapp:1.2            # Major.Minor tag (points to latest 1.2.x)
myapp:1              # Major tag (points to latest 1.x)
myapp:latest         # Most recent stable release
```

**Best practices**:
1. **Always use specific version tags** in production: `myapp:1.2.3`
2. **Use digests for critical deployments**: `myapp@sha256:abc123...`
3. **Never redeploy to the same tag** (immutable tags are safer)
4. **Record image digests in CI/CD** for rollback capability

**CI/CD approach**:
```bash
# Build with version tag
docker build -t myapp:${CI_COMMIT_SHORT_SHA} .
docker tag myapp:${CI_COMMIT_SHORT_SHA} myapp:latest

# Record digest
docker images --digests myapp:${CI_COMMIT_SHORT_SHA}
```

### Q26: How do you roll back to a previous image version?

**Answer:**
Multiple strategies for rollback depending on your deployment environment :

**Strategy 1: Re-deploy previous tag**
```bash
# If using version tags
kubectl set image deployment/myapp myapp=myapp:1.2.2
```

**Strategy 2: Use image digest** (most reliable)
```bash
# Recorded digest from successful deployment
kubectl set image deployment/myapp myapp=myapp@sha256:abc123...
```

**Strategy 3: Kubernetes rollout undo**
```bash
# If using Kubernetes with record
kubectl rollout history deployment/myapp
kubectl rollout undo deployment/myapp --to-revision=2
```

**Strategy 4: CI/CD re-run** previous pipeline with old tag

**Best practice**: Always record image digests in your CI/CD pipeline or Kubernetes annotations for reliable rollback .

### Q27: What is a scratch image and when would you use it?

**Answer:**
**`scratch`** is a special base image that represents an **empty filesystem** . It contains nothing—no shell, no libraries, no system tools.

**When to use scratch**:
- **Statically compiled binaries** (Go, Rust, C with static linking)
- **Minimal security requirements** (no attack surface)
- **Ultra-small images** (just your binary)

**Example with Go**:
```dockerfile
# Build stage
FROM golang:1.21 AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o myapp

# Runtime stage - empty!
FROM scratch
COPY --from=builder /app/myapp /myapp
ENTRYPOINT ["/myapp"]
```

**Considerations**:
- No shell means no debugging with `docker exec`
- No SSL certificates (may need to copy them)
- No timezone data
- Great for security, but requires fully self-contained binaries

### Q28: How do you create a minimal base image?

**Answer:**
Creating a minimal base image involves starting from `scratch` and adding only what's necessary :

**Method 1: From scratch with copied libraries**
```dockerfile
FROM scratch
COPY --from=busybox:latest /bin/sh /bin/sh
COPY --from=alpine:latest /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY mybinary /app/
```

**Method 2: Using Alpine as base** (already minimal)
```dockerfile
FROM alpine:3.19
RUN apk add --no-cache ca-certificates
COPY mybinary /app/
```

**Method 3: Using distroless images** (Google's minimal images)
```dockerfile
FROM gcr.io/distroless/base
COPY mybinary /app/
```

**Best practices for minimal images**:
- Use `scratch` for statically compiled binaries
- Use `alpine` when you need a package manager
- Use `distroless` for balanced security/functionality
- Never include package managers in production images

### Q29: How do you sign Docker images and why is it important?

**Answer:**
Image signing ensures **authenticity and integrity** of container images . Common tools include **Docker Content Trust (DCT)** and **Sigstore Cosign**.

**Docker Content Trust**:
```bash
# Enable DCT
export DOCKER_CONTENT_TRUST=1

# Push signed image
docker push myapp:1.2.3  # Automatically signed

# Pull only signed images
docker pull myapp:1.2.3  # Fails if not signed
```

**Cosign (Sigstore)**:
```bash
# Generate key pair
cosign generate-key-pair

# Sign image
cosign sign --key cosign.key myapp:1.2.3

# Verify
cosign verify --key cosign.pub myapp:1.2.3
```

**Why signing matters**:
- **Prevents tampering**: Ensures image wasn't modified after signing
- **Provenance**: Verifies who built/published the image
- **Supply chain security**: Critical for production deployments
- **Compliance**: Meets security audit requirements

**In Kubernetes**: Use admission controllers to enforce signed images only.

### Q30: How do you scan images for vulnerabilities?

**Answer:**
Image scanning identifies known vulnerabilities (CVEs) in base images and dependencies .

**Common scanning tools**:

| Tool | Type | Integration |
|------|------|-------------|
| **Trivy** | Open-source | CI/CD, local scanning |
| **Snyk** | Commercial | CI/CD, GitHub integration |
| **Clair** | Open-source | Registry scanning |
| **Docker Scout** | Built-in | Docker CLI, Docker Hub |
| **Grype** | Open-source | Local scanning |

**Example with Trivy**:
```bash
# Scan local image
trivy image myapp:1.2.3

# Scan with severity filter
trivy image --severity HIGH,CRITICAL myapp:1.2.3

# Generate HTML report
trivy image --format html --output report.html myapp:1.2.3
```

**CI/CD integration**:
```yaml
# GitHub Actions example
- name: Scan image
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: 'myapp:1.2.3'
    severity: 'CRITICAL'
    exit-code: '1'  # Fail if critical vulns found
```

**Best practices**:
- Scan at every build in CI/CD
- Scan nightly in registries
- Block deployment on critical vulnerabilities
- Regularly update base images

## Dockerfile Optimization Questions

### Q31: How do you reduce Docker image size?

**Answer:**
Multiple strategies for reducing image size :

| Strategy | Example | Size Impact |
|----------|---------|-------------|
| **Choose smaller base image** | `alpine` (5MB) vs `ubuntu` (77MB) | 70%+ reduction |
| **Multi-stage builds** | Separate build/run stages | 60-90% reduction |
| **Combine RUN commands** | `RUN apt-get update && apt-get install ... && rm -rf /var/lib/apt/lists/*` | Reduces layers |
| **Clean package managers** | Remove caches in same layer | Significant |
| **Use `.dockerignore`** | Exclude unnecessary files | Context size reduction |
| **Remove development dependencies** | `npm install --production` | 30-50% for Node.js |
| **Use specific tags** | `node:18-alpine` not `node:latest` | Consistent, smaller |

**Example optimization**:
```dockerfile
# BEFORE - 850MB
FROM node:18
WORKDIR /app
COPY . .
RUN npm install
RUN npm run build
CMD ["npm", "start"]

# AFTER - 210MB (75% reduction)
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:18-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
CMD ["node", "dist/index.js"]
```

### Q32: What is the purpose of .dockerignore file?

**Answer:**
The **`.dockerignore`** file specifies files and directories that should be **excluded** when sending the build context to the Docker daemon . It's similar to `.gitignore`.

**Why it's important**:
- **Smaller build context**: Faster `docker build`
- **Smaller images**: Unnecessary files aren't copied
- **Security**: Prevents secrets from being included
- **Faster CI/CD**: Less data to transfer

**Example .dockerignore**:
```
# Version control
.git
.gitignore

# Dependencies (rebuilt in container)
node_modules
vendor

# Environment files
.env
.env.local

# Build artifacts
dist
build
*.log

# IDE files
.vscode
.idea

# Docker files
Dockerfile
.dockerignore
README.md
```

**Best practice**: Always include `.dockerignore` in every project to prevent accidental inclusion of sensitive or unnecessary files.

### Q33: How do you optimize build cache usage?

**Answer:**
Optimizing build cache requires careful ordering of Dockerfile instructions :

**Cache optimization principles**:
1. **Least-changing instructions first**: Place infrequently changed steps early
2. **Copy dependencies before code**: Separate `package.json` from source code
3. **Combine `RUN` commands**: But only if they're related
4. **Use `--no-cache` when needed**: For fresh builds

**Optimized Dockerfile**:
```dockerfile
# GOOD - optimized for caching
FROM node:18-alpine

# 1. Copy dependency definitions first (rarely changes)
COPY package*.json ./

# 2. Install dependencies (cached unless package.json changes)
RUN npm ci --only=production

# 3. Copy source code (frequently changes) - last
COPY . .

# 4. Build application
RUN npm run build

CMD ["npm", "start"]
```

**Build with cache**:
```bash
# Normal build (uses cache)
docker build -t myapp .

# Force rebuild without cache
docker build --no-cache -t myapp .

# Build with specific cache sources
docker build --cache-from myapp:previous -t myapp .
```

### Q34: How do you handle environment-specific configurations?

**Answer:**
Multiple approaches for different environments (dev, staging, prod) :

**Strategy 1: Environment variables**

```dockerfile
# Dockerfile
FROM node:18-alpine
ENV NODE_ENV=production
CMD ["node", "app.js"]
```

**Runtime override**:
```bash
# Development
```

```dockerfile
# Dockerfile
```

**Strategy 3: Config files per environment**
```bash
# Mount different config files
docker run -v ./config.dev.json:/app/config.json myapp
```

### Q35: What are the security best practices for building Docker images?

**Answer:**
Comprehensive security practices for image building :

| Practice | Implementation | Why |
|----------|----------------|-----|
| **Use official base images** | `FROM node:18-alpine` not random images | Trusted, maintained |
| **Scan for vulnerabilities** | Trivy, Snyk in CI/CD | Find CVEs early |
| **Run as non-root** | Create and use `USER appuser` | Limit privileges |
| **Use specific tags** | `node:18-alpine` not `node:latest` | Reproducible builds |
| **Keep images small** | Alpine, multi-stage, `.dockerignore` | Smaller attack surface |
| **No secrets in images** | Never `COPY` secrets, use runtime injection | Prevent exposure |
| **Drop capabilities** | Docker run `--cap-drop ALL` | Least privilege |
| **Read-only root fs** | `--read-only` flag | Prevent file tampering |

**Secure Dockerfile example**:
```dockerfile
FROM node:18-alpine

# Create non-root user
RUN addgroup -g 1001 -S appgroup && \
    adduser -u 1001 -S appuser -G appgroup

WORKDIR /app

# Copy package files
COPY package*.json ./
RUN npm ci --only=production && npm cache clean --force

# Copy app files
COPY . .

# Change ownership
RUN chown -R appuser:appgroup /app

# Switch to non-root user
USER appuser

EXPOSE 3000
CMD ["node", "app.js"]
```

**Runtime security**:
```bash
docker run \
  --read-only \
  --tmpfs /tmp \
  --cap-drop ALL \
  --cap-add NET_BIND_SERVICE \
  --security-opt=no-new-privileges:true \
  myapp
```

## Image Troubleshooting Questions

### Q36: Your Docker build is failing. How do you troubleshoot?

**Answer:**
Systematic approach to debugging build failures :

**Step 1: Check build output**
```bash
# Build with detailed output
docker build --progress=plain -t myapp . 2>&1 | tee build.log
```

**Step 2: Identify the failing step**
Look for the last successful step before the error.

**Step 3: Run the failing step manually**
```bash
# Create a temporary container at the last successful state
docker run -it --entrypoint /bin/sh failed-build-stage

# Inside container, manually run the failing command
# This helps isolate environment issues
```

**Step 4: Common issues and fixes**:

| Issue | Likely Cause | Fix |
|-------|--------------|-----|
| **`COPY failed: file not found`** | Path issue, `.dockerignore` too aggressive | Check paths, verify build context |
| **`npm install` fails** | Network, missing dependencies | Check package.json, use `--network=host` |
| **Permission denied** | File permissions in container | Use `chmod` in Dockerfile |
| **No space left** | Layer cache filling disk | `docker builder prune` |
| **Syntax error** | Dockerfile instruction error | Check syntax, `RUN` commands |

**Step 5: Debug with `docker history`**
```bash
docker history failed-build-stage
```

### Q37: The image you built is too large. How do you analyze and reduce it?

**Answer:**
Systematic approach to analyzing and reducing image size :

**Step 1: Analyze image layers**
```bash
# Show layer sizes
docker history myapp:latest

# Use dive tool for interactive analysis
dive myapp:latest
```

**Step 2: Identify size culprits**:
- Unnecessary files (`.git`, `node_modules` already in image)
- Build dependencies (compilers, headers)
- Package manager caches (`/var/cache/apt/*`)
- Duplicate files across layers
- Heavy base images

**Step 3: Optimization checklist**:
- [ ] Using Alpine or slim base?
- [ ] Multi-stage build implemented?
- [ ] `.dockerignore` in place?
- [ ] RUN commands combined with cleanup?
- [ ] Only production dependencies installed?
- [ ] Unnecessary packages removed?

**Step 4: Measure improvement**
```bash
# Before and after comparison
docker images | grep myapp
```

**Example improvement tracking**:
```
Before: myapp    latest    850MB
After:  myapp    latest    210MB  (75% reduction)
```

### Q38: You need to update a dependency in an existing image without rebuilding everything. How?

**Answer:**
Several approaches depending on the situation :

**Option 1: Rebuild with cache** (preferred)
```bash
# Update package.json
# Build with cache - only changed layers rebuild
docker build -t myapp:new .
```

**Option 2: Run container and commit** (not recommended for production)
```bash
# Start container
docker run -it myapp:latest /bin/sh

# Inside container, update dependencies
apk update && apk add new-package

# Exit, then commit
docker commit container-id myapp:updated
```

**Why Option 2 is problematic**:
- Not reproducible
- No audit trail
- Hard to version control
- May include accidental changes

**Option 3: Use build args for versions**
```dockerfile
ARG NGINX_VERSION=1.25
FROM nginx:${NGINX_VERSION}-alpine
```

```bash
docker build --build-arg NGINX_VERSION=1.26 -t myapp .
```

**Best practice**: Always rebuild with updated Dockerfile rather than committing running containers.

### Q39: How do you find images that are using a specific base image?

**Answer:**
Several methods to find dependent images :

**Method 1: Inspect image history**
```bash
# Check if base image appears in history
docker history myapp:latest | grep ubuntu
```

**Method 2: Use `docker inspect`**
```bash
# Check parent image
docker inspect myapp:latest | jq '.[].Parent'

# Check image config
docker inspect myapp:latest | jq '.[].Config.Image'
```

**Method 3: Script to find all images using a base**
```bash
#!/bin/bash
BASE_IMAGE=$1
for image in $(docker images --format "{{.Repository}}:{{.Tag}}"); do
  if docker history $image 2>/dev/null | grep -q $BASE_IMAGE; then
    echo $image
  fi
done
```

**Method 4: Use `dive` to explore layers**
```bash
dive myapp:latest
# Shows all layers and their origin
```

### Q40: You pulled an image but can't find the tag you expected. What happened?

**Answer:**
Common scenarios and troubleshooting steps :

**Scenario 1: Tag was overwritten**
```bash
# Check if tag exists but points to different image
docker images --digests | grep myapp

# Pull by digest instead
docker pull myapp@sha256:abc123...
```

**Scenario 2: Image was deleted from registry**
```bash
# Try to pull with specific tag
docker pull myapp:1.2.3

# If 404, image or tag no longer exists
# Check registry web UI or API
```

**Scenario 3: Tag exists but not pulled locally**
```bash
# Force pull latest tag
docker pull myapp:1.2.3

# Check if remote tag exists
docker pull myapp:1.2.3 --dry-run
```

**Scenario 4: Wrong registry/repository**
```bash
# Check full image name
docker images | grep myapp

# Verify you're using correct registry
# myapp vs mycompany/myapp vs mycompany/myapp:tag
```

**Best practices to avoid issues**:
- Use specific tags, not `latest`
- Record digests for critical deployments
- Implement image retention policies
- Use immutable tags in production
