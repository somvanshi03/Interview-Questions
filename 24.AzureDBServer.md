#  Azure database services

## Part 1: Azure SQL Database (Basic to Intermediate)

### 1. What is Azure SQL Database and how does it differ from SQL Server?
**Answer:**
Azure SQL Database is a fully managed Platform-as-a-Service (PaaS) relational database engine from Microsoft . It handles most database management functions like upgrading, patching, backups, and monitoring without user involvement .

**Key differences from traditional SQL Server:**
- **Management:** Azure SQL Database automates backups, updates, and monitoring, whereas SQL Server requires manual setup for these features .
- **Scalability:** Azure SQL can scale vertically (changing DTUs/vCores) or horizontally (sharding) with minimal effort .
- **Availability:** Built-in high availability with 99.99% SLA, while on-premises SQL Server requires manual configuration of Always On Availability Groups.
- **Payment model:** Consumption-based pricing (pay for what you use) versus upfront licensing for SQL Server .

### 2. What are DTUs and how are they used in Azure SQL Database?
**Answer:**
DTU stands for Database Transaction Unit . It's a blended measure of compute resources that combines:
- CPU allocation
- Memory allocation
- Input/Output (I/O) rates

DTUs provide a simple way to understand the relative performance of Azure SQL databases across different service tiers . They help in:
- Gauging performance levels for database workloads
- Scaling databases up or down based on requirements
- Comparing performance across different pricing tiers

### 3. What is an elastic pool and when would you use it?
**Answer:**
An elastic pool is a cost-effective solution for managing multiple databases with varying and unpredictable usage patterns . It allows multiple databases to share a set of allocated resources .

**Key benefits:**
- **Cost optimization:** You pay for the pool's resources rather than each database individually .
- **Resource sharing:** Databases automatically consume resources as needed within configured limits.
- **Management simplicity:** Single point for scaling and monitoring multiple databases.

**Use case scenario:** A SaaS application with hundreds of databases, each with sporadic usage patterns where peak times vary across customers .

### 4. How does geo-replication work in Azure SQL Database?
**Answer:**
Geo-replication creates continuously synchronized readable secondary databases in different Azure regions . It provides:

- **Disaster recovery:** If the primary region fails, applications can fail over to a secondary region.
- **Read scalability:** Secondary databases can handle read-only query workloads, offloading the primary.
- **Data locality:** Users can access data from a geographically closer replica for better performance.

The feature automatically creates asynchronous replicas, and failover groups can be configured to manage failover of multiple databases as a single unit .

### 5. What security features does Azure SQL Database provide?
**Answer:**
Azure SQL Database offers multiple layers of security :

- **Network security:** Firewall rules restrict access by IP address; Virtual Network service endpoints isolate database traffic .
- **Authentication:** Azure Active Directory integration supports multi-factor authentication and single sign-on .
- **Data encryption:**
    - **Transparent Data Encryption (TDE):** Encrypts data at rest automatically without application changes .
    - **Always Encrypted:** Protects sensitive data even from database administrators.
- **Advanced threat protection:** Detects anomalous activities and potential threats.
- **Row-Level Security (RLS):** Restricts data access based on user characteristics .

## Part 2: Azure SQL Database (Advanced)

### 6. What is the difference between a single database, elastic pool, and managed instance?
**Answer:**
**Single Database:** A fully isolated database with its own dedicated resources. Best for modern cloud applications needing precise resource allocation .

**Elastic Pool:** Multiple databases sharing a resource set. Ideal for SaaS applications with databases having unpredictable usage patterns .

**Managed Instance:** A deployment option providing near 100% compatibility with on-premises SQL Server . It offers:
- Full SQL Server instance scope compatibility
- Support for SQL Agent Jobs, cross-database queries, and Linked Servers
- Easier lift-and-shift migration for existing applications 
- Virtual network isolation for enhanced security

### 7. How does Point-in-Time Restore work and what are its use cases?
**Answer:**
Point-in-Time Restore (PITR) allows recovering a database to any point within the retention period . It works by:

- Using automated backups taken every few minutes
- Applying transaction logs to a base backup to reconstruct database state at a specific timestamp
- Creating a new database during the restore process

**Use cases:**
- Recovering from human errors (accidental data deletion or updates) 
- Application bugs that corrupted data
- Compliance investigations requiring historical data views
- Creating development/test copies from production snapshots

### 8. How do Columnstore Indexes improve query performance?
**Answer:**
Columnstore indexes store data column-wise instead of traditional row-wise storage . This provides:

- **Massive compression:** Column-wise storage achieves 10x or better compression ratios
- **Faster scans:** Queries needing only specific columns read less data from disk
- **Batch processing:** Processes data in batches (millions of rows) rather than row-by-row

**Ideal workloads:** Data warehousing, analytics, reporting, and large fact tables where aggregation queries scan millions of rows .

### 9. How would you troubleshoot a critical performance issue in Azure SQL Database?
**Answer:**
When facing a performance issue, follow this systematic approach :

**1. Immediate investigation:**
- Check Azure Monitor and Query Performance Insight for high DTU utilization or slow queries
- Identify the specific queries causing resource spikes

**2. Root cause analysis:**
- Use Query Store to examine execution plan changes
- Check `sys.dm_exec_query_stats` for resource-intensive queries
- Look for plan regressions where a previously efficient query now uses a suboptimal plan

**3. Mitigation:**
- Force a known good execution plan for immediate relief 
- Identify missing indexes and create them
- Update statistics if outdated

**4. Prevention:**
- Configure Automatic Tuning to automatically address performance issues
- Implement proactive monitoring alerts
- Review and optimize indexes regularly

### 10. How do you design a disaster recovery strategy with specific RTO and RPO objectives?
**Answer:**
For critical databases requiring aggressive RTO (e.g., 30 minutes) and RPO (e.g., 5 minutes) objectives :

**Azure SQL Database approach:**
- Configure **Active Geo-Replication** to create continuously synchronized secondaries in a paired region
- Group databases into **Auto-Failover Groups** for managing failover as a unit
- Enable automatic failover policy with appropriate grace period

**Azure SQL Managed Instance approach:**
- Use **Failover Groups** leveraging distributed availability groups
- Ensure secondary region is within acceptable latency limits

**Implementation steps :**
1. Select geographically distant secondary region
2. Configure continuous synchronization with readable secondary replicas
3. Set up failover groups with single connection endpoints (read-write listener)
4. Configure automatic failover with appropriate grace period
5. Regularly test failover procedures through drills

## Part 3: Azure Cosmos DB (Basic to Intermediate)

### 11. What is Azure Cosmos DB and what are its core features?
**Answer:**
Azure Cosmos DB is a globally distributed, multi-model database service designed for elastic scaling and low-latency access .

**Core features:**
- **Global distribution:** Replicate data across Azure regions with a single click 
- **Multi-model support:** Document, key-value, graph, and column-family data models 
- **Multi-API support:** SQL, MongoDB, Cassandra, Gremlin (graph), Table, and Etcd APIs 
- **Automatic indexing:** No manual index management required
- **ACID transactions:** Multi-document transaction support
- **SLA-backed performance:** Guaranteed latency at the 99th percentile
- **Tunable consistency:** Five consistency levels to balance consistency, availability, and performance

### 12. What is a Request Unit (RU) in Cosmos DB?
**Answer:**
A Request Unit (RU) is a normalized measure of the resources (CPU, memory, I/O) required to perform database operations .

**Key concepts:**
- **1 RU** typically equals a simple read of a 1KB item
- Complex queries consume more RUs (e.g., 5-10 RUs for range queries)
- **Provisioned RU mode:** Allocate specific RU/second capacity, billed hourly
- **Serverless mode:** Pay only for RUs consumed

**RU consumption factors:**
- Item size (larger items require more RUs)
- Property count and indexing settings
- Query complexity (joins, aggregations increase RU cost)
- Consistency level (strong consistency costs more)

**Example code to check RU consumption :**
```csharp
var response = await query.ExecuteNextAsync();
Console.WriteLine($"Request Charge: {response.RequestCharge} RUs");
```

### 13. Explain the different APIs provided by Cosmos DB and how to choose the right one
**Answer:**
Cosmos DB offers multiple APIs, each optimized for specific data models :

**API Offerings:**

| API | Data Model | Best For |
|-----|------------|----------|
| **Core (SQL)** | JSON documents | General-purpose applications needing SQL-like querying |
| **MongoDB** | BSON documents | Migrating MongoDB applications with minimal code changes |
| **Cassandra** | Column-family | Applications already using Cassandra/CQL |
| **Gremlin** | Graph data | Social networks, recommendation engines, fraud detection |
| **Table** | Key-value | Applications using Azure Table Storage |

**Selection factors :**
- **Data model:** Choose based on how your application naturally structures data
- **Existing ecosystem:** Leverage existing team expertise (e.g., MongoDB developers)
- **Querying needs:** SQL and Gremlin offer richer query capabilities
- **Migration requirements:** Minimize code changes when migrating existing applications

### 14. What is the data model used by Cosmos DB and how does it differ from relational databases?
**Answer:**
Cosmos DB uses a document-oriented data model where each record is a self-contained hierarchical unit called a document (typically JSON) .

**Key differences from relational databases :**

| Feature | Cosmos DB | Relational Databases |
|---------|-----------|---------------------|
| **Structure** | Self-contained documents | Normalized tables with relationships |
| **Schema** | Flexible, schema-agnostic | Rigid schemas defined upfront |
| **Relationships** | Embedded or referenced | Foreign keys, join tables |
| **Query language** | SQL-like on documents | SQL |
| **Transactions** | Atomic within a document | Multi-table transactions |

**Document example :**
```json
{
  "id": "1",
  "name": "John Doe",
  "addresses": [
    {"street": "123 Main St", "city": "Anytown"},
    {"street": "456 Elm St", "city": "Othertown"}
  ],
  "contact": {
    "email": "john@example.com",
    "phone": "123-456-7890"
  }
}
```

This embedded approach reduces need for joins and improves read performance.

## Part 4: Azure Cosmos DB (Advanced)

### 15. Explain the CAP theorem and how Cosmos DB implements tunable consistency
**Answer:**
The CAP theorem states that a distributed database can achieve only two of three guarantees: Consistency, Availability, and Partition Tolerance .

**Azure Cosmos DB implements five tunable consistency levels** to navigate this trade-off :

**1. Strong:**
- Guarantees linearizability; reads always see latest writes
- Highest consistency, highest latency, least available during partitions

**2. Bounded Staleness:**
- Reads lag behind writes by at most X versions or Y time interval
- Good compromise for applications needing strong ordering

**3. Session (Default):**
- Guarantees consistency for a single user session
- If you write, you'll read your write; others may see eventual consistency

**4. Consistent Prefix:**
- Updates appear in order, never out-of-order
- If writes are A → B → C, you'll never see B → A or C → A → B 

**5. Eventual:**
- No ordering guarantees; reads may return stale data
- Lowest latency, highest availability

**Analogy :** Like a DNS system after domain registration—updates propagate gradually but eventually reach all servers.

### 16. How does Cosmos DB ensure data durability?
**Answer:**
Cosmos DB ensures data durability through multiple mechanisms :

**Write-Ahead Logging (WAL):**
- All changes are recorded in a log before writing to disk
- Log is continuously synced to guarantee persistence even during system crashes

**Log-structured storage:**
- Data stored in log-structured format with compaction logs for cleanup
- Maintains data consistency during reorganization

**Multi-Version Concurrency Control (MVCC):**
- Old versions preserved until safe to discard
- Enables snapshot isolation for transactions

**Automated backups:**
- Point-in-time backups captured automatically at regular intervals
- Configurable retention periods
- Geo-redundancy for cross-region durability

**Multi-region replication:**
- Data replicated synchronously or asynchronously across regions
- Survives regional disasters through automatic failover

### 17. What are the different scaling options in Cosmos DB?
**Answer:**
Cosmos DB offers both vertical and horizontal scaling capabilities :

**Throughput scaling:**
- **Provisioned throughput:** Set RU/second for a container or database
- **Auto-scale:** Automatically scales RU/s within defined ranges based on traffic
- **Serverless:** Pay only for consumed RUs, ideal for intermittent workloads

**Storage scaling:**
- **Horizontal partitioning:** Data automatically distributed across physical partitions
- **Logical partitions:** Based on partition key selection
- **Unlimited storage:** Scale to petabytes by adding more partitions

**Global distribution:**
- Add/remove regions at any time with no downtime
- Multi-region writes for active-active configurations
- Automatic failover for regional outages

### 18. How do you choose the right partition key in Cosmos DB?
**Answer:**
Partition key selection is critical for performance and scalability:

**Best practices:**
- **Choose high cardinality properties** (many distinct values) to distribute workload evenly
- **Select properties frequently used in queries** (queries should include partition key when possible)
- **Avoid "hot partitions"** by ensuring even data distribution

**Examples:**
- ✅ Good: UserId (millions of distinct values, commonly queried)
- ✅ Good: DeviceId in IoT scenarios (wide distribution)
- ❌ Bad: Status (few values like "Active"/"Inactive" creates hot partitions)
- ❌ Bad: Date (all data for same date on one partition)

**If you choose poorly:**
- Storage limits per logical partition (20GB max)
- Throughput throttling on hot partitions
- Inefficient cross-partition queries

### 19. How does Cosmos DB handle multi-document transactions?
**Answer:**
Cosmos DB supports multi-document transactions with ACID guarantees within the same logical partition :

**Transactional capabilities:**
- **Atomicity:** All operations in a transaction succeed or fail together
- **Consistency:** Isolation levels based on chosen consistency model
- **Isolation:** Changes not visible outside transaction until committed
- **Durability:** Committed changes persist even after failures

**Limitations:**
- Transactions limited to items in the same logical partition (same partition key value)
- Cross-partition transactions not supported
- Use stored procedures for transactional operations

**Implementation:**
- Stored procedures execute within transactional scope
- JavaScript stored procedures in Cosmos DB provide transactional guarantees

## Part 5: Azure Database for MySQL and PostgreSQL

### 20. How do you handle transient connection errors in Azure Database for MySQL?
**Answer:**
Transient errors are temporary failures that resolve themselves (network glitches, failovers, etc.). Applications should implement retry logic .

**Best practice retry strategy:**
1. **Wait before retrying:** First retry after 5 seconds 
2. **Exponential backoff:** Increase wait time exponentially up to 60-120 seconds 
3. **Maximum attempts:** Set a limit (e.g., 10 attempts) after which application reports failure 

**Implementation pattern :**
```csharp
// Conceptual retry logic
int maxAttempts = 10;
int delay = 5; // seconds

for (int attempt = 1; attempt <= maxAttempts; attempt++)
{
    try
    {
        // Attempt database connection
        break; // Success - exit loop
    }
    catch (TransientException)
    {
        if (attempt == maxAttempts) throw;
        Thread.Sleep(delay * 1000);
        delay = Math.Min(delay * 2, 120); // Exponential backoff
    }
}
```

### 21. What is logical replication in Azure Database for PostgreSQL?
**Answer:**
Logical replication is a method of replicating data objects and their changes based on replication identity (usually primary key) .

**Key characteristics:**
- **Granular control:** Replicate specific tables or sets of tables 
- **Flexible targets:** Can replicate to external systems outside PostgreSQL
- **WAL-based:** Uses Write-Ahead Log (WAL) as the source of changes 
- **Version independent:** Source and target can run different PostgreSQL versions

**Use cases:**
- Replicating to reporting/analytics systems
- Upgrading PostgreSQL versions with minimal downtime
- Selective data distribution to different applications

### 22. How do you migrate an on-premises PostgreSQL database to Azure?
**Answer:**
Multiple migration strategies exist depending on requirements:

**Azure Database Migration Service (DMS):**
- Supports online migrations with minimal downtime
- Continuously synchronizes changes during migration
- Validates source compatibility before migration

**pg_dump / pg_restore:**
- Simple approach for smaller databases
- Suitable for offline migrations
- Example: `pg_dump -Fc source_db > backup.dump` then restore in Azure

**Azure Data Factory:**
- Orchestrates data movement with transformations if needed
- Supports incremental loads 

**Considerations:**
- **Compatibility:** Check for unsupported features using Azure Migrate
- **Network:** Set up VPN or ExpressRoute for secure transfer
- **Testing:** Always validate in staging environment first
- **Cutover planning:** Define rollback strategy and validation steps

## Part 6: General Database Management and Migration

### 23. What tools does Azure provide for database migration?
**Answer:**
Azure offers several tools for different migration scenarios :

**Data Migration Assistant (DMA):**
- Assesses on-premises SQL Server for compatibility issues
- Identifies feature parity gaps and migration blockers 
- Recommends target Azure SQL tier and size

**Azure Database Migration Service (DMS):**
- Orchestrates online/offline migrations with minimal downtime 
- Supports heterogeneous migrations (SQL Server to MySQL/PostgreSQL)
- Handles complex migrations with continuous synchronization

**Azure Data Factory (ADF):**
- Cloud-based data integration service 
- Moves data from on-premises to Azure SQL 
- Orchestrates pipelines with activities, datasets, and linked services
- Handles incremental data loads 
- Supports data transformations using Data Flows 

**SQL Server Migration Assistant (SSMA):**
- Automates migration to Azure SQL for Oracle, MySQL, PostgreSQL sources
- Converts database schema and migrates data

**Bulk Copy Program (BCP):**
- Bulk imports/exports data for SQL Server 
- Suitable for large datasets

### 24. How do you design for high availability across different Azure database services?
**Answer:**
Different Azure databases offer different HA mechanisms:

**Azure SQL Database :**
- **Active Geo-Replication:** Readable secondaries in different regions
- **Auto-Failover Groups:** Group failover with single connection endpoint
- **Zone-redundant configuration:** Replicas across availability zones within region

**Azure SQL Managed Instance :**
- **Failover Groups:** Based on distributed availability groups
- **Auto-failover:** Regional outage triggers automatic failover

**Azure Cosmos DB :**
- **Multi-region writes:** Active-active configuration for continuous availability
- **Automatic failover:** Traffic redirects to available regions
- **SLA-backed:** 99.999% read availability with multiple regions

**Azure Database for MySQL/PostgreSQL:**
- **Read replicas:** Create replicas in same/different region
- **Zone-redundant HA:** Automatic failover to standby in different zone

**Best practices:**
- Define RTO/RPO requirements first 
- Test failover procedures regularly
- Monitor replication lag and health

### 25. How do you optimize query performance across different Azure databases?
**Answer:**
Optimization strategies vary by database type:

**Azure SQL Database :**
- **Query Store:** Track performance over time and identify regressions
- **Automatic Tuning:** Automatically address performance issues
- **Index optimization:** Create missing indexes, remove unused ones
- **Parameter sniffing:** Address with OPTIMIZE FOR UNKNOWN hints
- **Partitioning:** Large tables for better manageability

**Azure Cosmos DB :**
- **Partition key selection:** Ensure even distribution
- **Indexing policy:** Optimize which properties are indexed
- **Query efficiency:** Use partition keys in filters, avoid cross-partition queries
- **RU optimization:** Measure request charges and tune queries

**General approach :**
1. **Identify bottlenecks:** Use built-in monitoring tools
2. **Analyze execution:** Review query plans and statistics
3. **Implement fixes:** Indexes, query rewrites, schema adjustments
4. **Validate improvement:** Compare before/after metrics
5. **Prevent recurrence:** Automated monitoring and alerts
