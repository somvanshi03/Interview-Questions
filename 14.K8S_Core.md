## Core Kubernetes Objects Overview

### Q1: What is a Kubernetes object and what are its key fields?

**Answer:**
A **Kubernetes object** is a persistent entity in the Kubernetes system that represents the state of your cluster . These objects describe what containerized applications are running, their available resources, and policies around them.

**Every Kubernetes object has two main sections**:

```yaml
apiVersion: v1          # Kubernetes API version
kind: Pod               # Type of object
metadata:               # Identification data
  name: my-pod
  namespace: default
  labels:
    app: web
spec:                    # Desired state
  containers:
  - name: nginx
    image: nginx:1.21
```

| Section | Purpose | Common Fields |
|---------|---------|---------------|
| **apiVersion** | API version to use | `v1`, `apps/v1`, `batch/v1` |
| **kind** | Object type | `Pod`, `Deployment`, `Service` |
| **metadata** | Object identification | `name`, `namespace`, `labels`, `annotations` |
| **spec** | Desired configuration | Varies by object type |
| **status** (read-only) | Current state | Populated by Kubernetes |

### Q2: How does Kubernetes maintain desired state?

**Answer:**
Kubernetes uses a **declarative model** and **control loops** to maintain desired state :

1. **User declares desired state** via YAML/JSON (e.g., "I want 3 replicas of nginx")
2. **API server stores** this desired state in etcd
3. **Controllers continuously watch** for differences between desired and actual state
4. **Controllers take action** to reconcile the differences

**Example reconciliation**:
- Desired: 3 replicas
- Actual: 2 replicas (one pod crashed)
- Controller action: Create a new pod to reach 3

This is why Kubernetes is called a **self-healing system**—it constantly works to make actual state match desired state.

## Workloads Objects

### Q3: What is a Pod and what are its core characteristics?

**Answer:**
A **Pod** is the smallest and simplest deployable unit in Kubernetes . It represents a single instance of a running process and encapsulates one or more containers.

**Core characteristics**:
- **Shared network**: Containers in a Pod share the same IP address and port space (can communicate via `localhost`)
- **Shared storage**: Can share volumes mounted at the same path
- **Atomic scheduling**: All containers in a Pod are scheduled together on the same node
- **Ephemeral nature**: Pods can be created, destroyed, and replaced dynamically

**When to use multiple containers in one Pod**:
- Sidecar pattern (logging agent, proxy)
- Adapter pattern (transforming data)
- Ambassador pattern (proxying to external services)

**Example**:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: two-container-pod
spec:
  containers:
  - name: web
    image: nginx
    ports:
    - containerPort: 80
  - name: sidecar
    image: fluentd
    volumeMounts:
    - name: logs
      mountPath: /logs
  volumes:
  - name: logs
    emptyDir: {}
```

### Q4: What is a ReplicaSet and how does it work?

**Answer:**
A **ReplicaSet** ensures that a specified number of Pod replicas are running at any given time . It acts as a pod-level auto-healer.

**Key fields**:
- **replicas**: Desired number of Pods
- **selector**: Label selector to identify Pods to manage
- **template**: Pod template for creating new Pods

**How it works**:
1. ReplicaSet controller watches for Pods matching its selector
2. If too few Pods, it creates new ones from the template
3. If too many, it deletes excess Pods

**Important**: ReplicaSets are typically not used directly—**Deployments** manage ReplicaSets and provide additional features like rolling updates.

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: frontend
spec:
  replicas: 3
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      containers:
      - name: nginx
        image: nginx:1.21
```

### Q5: Explain Deployment and its core functionality

**Answer:**
A **Deployment** is a higher-level abstraction that manages ReplicaSets and provides declarative updates for Pods . It's the most common way to deploy stateless applications.

**Core functionality**:
- **Rolling updates**: Gradually replace old Pods with new ones without downtime
- **Rollbacks**: Easily revert to a previous version
- **Scaling**: Increase or decrease replicas
- **Pause/resume**: Pause rollout to investigate issues
- **Self-healing**: Replaces failed Pods

**Deployment strategies**:

| Strategy | Description | Use Case |
|----------|-------------|----------|
| **RollingUpdate** (default) | Gradually replaces Pods | Zero-downtime updates |
| **Recreate** | Deletes all old Pods before creating new ones | When downtime is acceptable |

**Example**:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.21
        ports:
        - containerPort: 80
```

### Q6: What is a StatefulSet and when would you use it?

**Answer:**
A **StatefulSet** is the workload API object used to manage stateful applications . Unlike Deployments, StatefulSets provide:

**Key features**:
- **Stable network identity**: Each Pod gets a predictable name (`podname-0`, `podname-1`)
- **Stable persistent storage**: Each Pod can have its own PersistentVolume that persists across rescheduling
- **Ordered deployment/scaling**: Pods are created, updated, and deleted in order
- **Ordered graceful deletion**: Pods are terminated in reverse order

**When to use StatefulSet**:
- Databases (MySQL, PostgreSQL, Cassandra)
- Distributed systems (Kafka, ZooKeeper, Elasticsearch)
- Any application requiring stable network identifiers and persistent storage

**Example**:
```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  serviceName: "nginx"
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.21
        volumeMounts:
        - name: www
          mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
  - metadata:
      name: www
    spec:
      accessModes: [ "ReadWriteOnce" ]
      resources:
        requests:
          storage: 1Gi
```

### Q7: What is a DaemonSet and what are common use cases?

**Answer:**
A **DaemonSet** ensures that all (or some) Nodes run a copy of a specific Pod . As nodes are added to the cluster, Pods are added; as nodes are removed, Pods are garbage collected.

**Common use cases**:
- **Log collection**: Run Fluentd or Filebeat on every node
- **Monitoring**: Deploy Node Exporter or Prometheus node agents
- **Networking**: Deploy CNI plugins (Calico, Weave) or kube-proxy alternatives
- **Storage**: Run glusterd, ceph, or other storage daemons
- **Security**: Run node-level security agents (Falco, AppArmor)

**Example**:
```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd
spec:
  selector:
    matchLabels:
      name: fluentd
  template:
    metadata:
      labels:
        name: fluentd
    spec:
      containers:
      - name: fluentd
        image: fluent/fluentd:v1.16
        volumeMounts:
        - name: varlog
          mountPath: /var/log
      volumes:
      - name: varlog
        hostPath:
          path: /var/log
```

### Q8: What are Jobs and CronJobs in Kubernetes?

**Answer:**
**Jobs** are Kubernetes objects designed for batch processing tasks that run to completion . Unlike Deployments (which aim to keep Pods running), Jobs ensure a specified number of Pods successfully terminate.

**Job types**:

| Type | Description | Example |
|------|-------------|---------|
| **Non-parallel** | One Pod runs once | Database migration |
| **Parallel with fixed count** | Multiple Pods, all must succeed | Batch processing |
| **Parallel with work queue** | Multiple Pods, any can complete | Queue processing |

**CronJobs** are Jobs that run on a scheduled basis, similar to cron in Linux.

**Job example**:
```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: pi
spec:
  completions: 5
  parallelism: 2
  template:
    spec:
      containers:
      - name: pi
        image: perl:5.34
        command: ["perl", "-Mbignum=bpi", "-wle", "print bpi(2000)"]
      restartPolicy: Never
```

**CronJob example**:
```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup
spec:
  schedule: "0 2 * * *"  # Daily at 2 AM
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup
            image: backup-tool:latest
            command: ["/backup.sh"]
          restartPolicy: OnFailure
```

## Service & Networking Objects

### Q9: What is a Service and what problem does it solve?

**Answer:**
A **Service** is an abstraction that defines a logical set of Pods and a policy for accessing them . Services solve several problems:

**Problems solved by Services**:
1. **Pod ephemerality**: Pods come and go, their IPs change
2. **Service discovery**: How do clients find Pods?
3. **Load balancing**: Distribute traffic across multiple Pods
4. **Stable endpoint**: Provide a fixed IP/DNS name

**How Services work**:
- Service selects Pods using label selectors
- Endpoint controller creates Endpoints object with Pod IPs
- kube-proxy programs node iptables/IPVS to route traffic
- Clients access Service IP/name, not individual Pod IPs

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    app: nginx
  ports:
  - protocol: TCP
    port: 80        # Service port
    targetPort: 8080 # Container port
  type: ClusterIP
```

### Q10: Explain the different Service types

**Answer:**
Kubernetes provides four Service types for different access needs :

| Type | Description | Access | Use Case |
|------|-------------|--------|----------|
| **ClusterIP** (default) | Exposes Service on cluster-internal IP | Only within cluster | Internal services, databases |
| **NodePort** | Exposes Service on static port on each Node | External (NodeIP:NodePort) | Development, simple external access |
| **LoadBalancer** | Provisions external cloud load balancer | External via cloud LB | Production services with cloud provider |
| **ExternalName** | Maps Service to external DNS name | External via CNAME | Accessing external services |

**NodePort example**:
```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  type: NodePort
  selector:
    app: nginx
  ports:
  - port: 80
    targetPort: 80
    nodePort: 30080  # Optional, defaults to 30000-32767
```

**ExternalName example**:
```yaml
apiVersion: v1
kind: Service
metadata:
  name: external-db
spec:
  type: ExternalName
  externalName: database.example.com  # CNAME to this
```

### Q11: What is an Ingress and when would you use it?

**Answer:**
**Ingress** is an API object that manages external access to Services, typically HTTP/HTTPS . It provides:
- **Host-based routing**: `app1.example.com` → Service A
- **Path-based routing**: `/api` → Service B, `/web` → Service C
- **TLS termination**: HTTPS certificates
- **Load balancing**: Across multiple Services

**When to use Ingress**:
- Multiple services need to be exposed externally
- You need TLS/SSL termination
- You want path-based or host-based routing
- You're using a single load balancer for multiple services (cost-effective)

**Important**: Ingress requires an **Ingress Controller** (like NGINX Ingress, Traefik, or AWS ALB Ingress Controller) to work.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
spec:
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 80
      - path: /web
        pathType: Prefix
        backend:
          service:
            name: web-service
            port:
              number: 80
  tls:
  - hosts:
    - app.example.com
    secretName: app-tls-secret
```

### Q12: What are Endpoints and EndpointSlices?

**Answer:**
**Endpoints** and **EndpointSlices** track the actual IP addresses of Pods backing a Service .

**Endpoints (traditional)**:
- Created automatically when a Service has a selector
- List all Pod IPs matching the Service's selector
- Simple list format

```yaml
apiVersion: v1
kind: Endpoints
metadata:
  name: my-service
subsets:
- addresses:
  - ip: 10.244.1.10
    targetRef:
      kind: Pod
      name: nginx-1
  - ip: 10.244.2.11
    targetRef:
      kind: Pod
      name: nginx-2
  ports:
  - port: 80
    protocol: TCP
```

**EndpointSlices (modern)**:
- Introduced for better scalability
- Split endpoints into slices (default 100 per slice)
- Better for large clusters (thousands of endpoints)

**Why EndpointSlices matter**: In large clusters with thousands of Services and endpoints, Endpoints objects could become huge and cause performance issues. EndpointSlices distribute this data.

### Q13: What is a NetworkPolicy and how does it work?

**Answer:**
**NetworkPolicy** is a specification that defines how Pods are allowed to communicate with each other and with external endpoints . It acts as a firewall for Pods.

**How it works**:
- Network policies are implemented by a CNI plugin that supports them (Calico, Cilium)
- By default, Pods accept traffic from any source (no isolation)
- Once a Pod is selected by any NetworkPolicy, it becomes isolated and only accepts traffic allowed by its policies

**Policy types**:
- **Ingress**: Incoming traffic to Pods
- **Egress**: Outgoing traffic from Pods

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-policy
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 3306
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: database
    ports:
    - protocol: TCP
      port: 5432
```

## Configuration & Storage Objects

### Q14: What are ConfigMaps and how are they used?

**Answer:**
**ConfigMaps** are Kubernetes objects used to store non-sensitive configuration data in key-value pairs . They decouple configuration from container images, making applications more portable.

**Ways to use ConfigMaps**:

1. **Environment variables**:
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  log_level: debug
  api_url: https://api.example.com
```

```yaml
# In Pod
env:
- name: LOG_LEVEL
  valueFrom:
    configMapKeyRef:
      name: app-config
      key: log_level
```

2. **Configuration files** (mounted as volumes):
```yaml
# In Pod
volumes:
- name: config
  configMap:
    name: app-config
    items:
    - key: config.json
      path: config.json
```

3. **Command-line arguments**:
```yaml
args: ["--log-level=$(LOG_LEVEL)"]
```

### Q15: What are Secrets and how do they differ from ConfigMaps?

**Answer:**
**Secrets** are similar to ConfigMaps but designed for sensitive data like passwords, API keys, and certificates .

| Aspect | ConfigMap | Secret |
|--------|----------|--------|
| **Data encoding** | Plain text | Base64 encoded (can be encrypted at rest) |
| **Purpose** | Non-sensitive configuration | Sensitive data |
| **Size limit** | 1 MiB | 1 MiB |
| **Use cases** | Config files, env vars | Credentials, tokens, SSH keys |

**Secret example**:
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  username: YWRtaW4=  # "admin" in base64
  password: MWYyZDFlMmU2N2Rm  # "1f2d1e2e67df" in base64
```

**StringData alternative** (easier to read, converted to data automatically):
```yaml
apiVersion: v1
kind: Secret
stringData:
  username: admin
  password: 1f2d1e2e67df
```

**Secret types**:
- **Opaque**: Generic secrets (default)
- **kubernetes.io/service-account-token**: Service account tokens
- **kubernetes.io/dockerconfigjson**: Docker registry credentials
- **kubernetes.io/tls**: TLS certificates

### Q16: What are PersistentVolumes (PVs) and PersistentVolumeClaims (PVCs)?

**Answer:**
**PersistentVolumes (PVs)** are cluster resources that provide storage independent of Pod lifecycles . They are provisioned by administrators or dynamically via StorageClasses.

**PersistentVolumeClaims (PVCs)** are requests for storage by users . They specify size, access modes, and storage class.

**Access Modes**:
- **ReadWriteOnce (RWO)**: Read-write by a single node
- **ReadOnlyMany (ROX)**: Read-only by many nodes
- **ReadWriteMany (RWX)**: Read-write by many nodes

**PV example** (static provisioning):
```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-example
spec:
  capacity:
    storage: 10Gi
  volumeMode: Filesystem
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  hostPath:
    path: /mnt/data
```

**PVC example**:
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-example
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 8Gi
  storageClassName: standard
```

**PVC in a Pod**:
```yaml
apiVersion: v1
kind: Pod
spec:
  containers:
  - name: app
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: pvc-example
```

### Q17: What is a StorageClass and why is it important?

**Answer:**
**StorageClass** enables dynamic provisioning of PersistentVolumes . It defines the "class" of storage (SSD, standard, etc.) and the provisioner to use.

**Key fields**:
- **provisioner**: Which storage backend to use (e.g., `kubernetes.io/aws-ebs`, `kubernetes.io/gce-pd`)
- **parameters**: Provisioner-specific configuration
- **reclaimPolicy**: What to do with PV when PVC is deleted (Delete/Retain)

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
provisioner: kubernetes.io/aws-ebs
parameters:
  type: gp3
  fsType: ext4
  iopsPerGB: "10"
reclaimPolicy: Delete
allowVolumeExpansion: true
```

**Why StorageClass matters**:
- **Automation**: No manual PV creation
- **Flexibility**: Users can request specific storage types
- **Cloud integration**: Works with cloud provider storage
- **Scalability**: Easy to provision storage for many PVCs

**Using StorageClass**:
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
spec:
  storageClassName: fast  # Use the StorageClass
  resources:
    requests:
      storage: 100Gi
```

## Cluster & Metadata Objects

### Q18: What are Namespaces and how do they work?

**Answer:**
**Namespaces** are virtual clusters within a physical Kubernetes cluster . They provide a way to divide cluster resources between multiple users, teams, or projects.

**Core functionality**:
- **Resource isolation**: Separate environments (dev, staging, prod)
- **Access control**: RBAC policies scoped to namespaces
- **Resource quotas**: Limit resources per namespace
- **Network isolation**: NetworkPolicies can restrict cross-namespace traffic

**Built-in namespaces**:
- **default**: Default namespace for objects with no other namespace
- **kube-system**: Namespace for objects created by Kubernetes system
- **kube-public**: Readable by all users (reserved for cluster usage)
- **kube-node-lease**: For node heartbeat leases

**Creating and using namespaces**:
```bash
kubectl create namespace team-a
kubectl get pods -n team-a
kubectl config set-context --current --namespace=team-a
```

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    environment: prod
```

### Q19: What are Labels and Selectors?

**Answer:**
**Labels** are key/value pairs attached to Kubernetes objects for identification and organization . **Selectors** are used to filter objects based on these labels.

**Label examples**:
```yaml
metadata:
  labels:
    environment: production
    app: nginx
    tier: frontend
    version: "1.21"
    release: stable
```

**Selector types**:

| Selector Type | Example | Usage |
|--------------|---------|-------|
| **Equality-based** | `environment=production` | Services, Deployments |
| **Set-based** | `environment in (production, staging)` | NetworkPolicies, Jobs |

**Using selectors**:
```bash
# Equality-based
kubectl get pods -l environment=production

# Set-based
kubectl get pods -l 'environment in (production, staging)'

# Multiple conditions
kubectl get pods -l 'environment=production,app=nginx'
```

**In YAML**:
```yaml
# Service selecting pods with app=nginx
selector:
  matchLabels:
    app: nginx
```

### Q20: What are Annotations and how do they differ from Labels?

**Answer:**
**Annotations** are key/value metadata attached to objects, but unlike labels, they are **not used for identification or selection** . Annotations are for non-identifying information.

| Aspect | Labels | Annotations |
|--------|--------|-------------|
| **Purpose** | Identification, selection, grouping | Non-identifying metadata |
| **Queryable** | Yes (via label selectors) | No |
| **Use cases** | Service discovery, pod selection | Tool-specific metadata, build info |
| **Size limit** | 63 characters (name), 253 (value) | No strict limit |

**Common annotation uses**:
- Build timestamps, commit hashes
- Contact information (owner, team)
- Tool-specific configuration (ingress controllers)
- Deployment strategies (canary weights)
- Monitoring hints (scrape intervals)

```yaml
metadata:
  annotations:
    kubernetes.io/ingress.class: nginx
    nginx.ingress.kubernetes.io/rewrite-target: /
    deployment.kubernetes.io/revision: "1"
    prometheus.io/scrape: "true"
    prometheus.io/port: "8080"
    git-commit: "2d3e4f5"
    build-url: "https://jenkins/job/123"
```

### Q21: What is a LimitRange?

**Answer:**
**LimitRange** provides constraints on resource requests and limits at the namespace level . It ensures individual Pods/containers don't consume excessive resources.

**What LimitRange can enforce**:
- **Min/max resource constraints** for Pods/containers
- **Default requests/limits** when not specified
- **Ratio constraints** (e.g., limit must be >= request)

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: resource-limits
  namespace: dev
spec:
  limits:
  - max:
      cpu: "2"
      memory: 4Gi
    min:
      cpu: "100m"
      memory: 256Mi
    default:
      cpu: "500m"
      memory: 1Gi
    defaultRequest:
      cpu: "200m"
      memory: 512Mi
    type: Container
```

**Why LimitRange matters**:
- Prevents resource exhaustion by a single Pod
- Ensures all Pods have reasonable resource settings
- Provides defaults for users who forget to specify

### Q22: What is a ResourceQuota?

**Answer:**
**ResourceQuota** provides constraints on **aggregate resource consumption** per namespace . Unlike LimitRange (per Pod), ResourceQuota limits the total resources across all objects.

**What ResourceQuota can limit**:
- **Compute resources**: Total CPU/memory requests and limits
- **Storage resources**: Total PVC storage
- **Object counts**: Max number of Pods, Services, ConfigMaps, etc.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-quota
  namespace: dev
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    persistentvolumeclaims: "5"
    pods: "10"
    services: "10"
    configmaps: "20"
```

**Using both LimitRange and ResourceQuota**:
- **LimitRange**: Prevents any single Pod from being too large
- **ResourceQuota**: Prevents total resources from exceeding limits
- Together they provide comprehensive resource governance

## Security & Access Control Objects

### Q23: What is a ServiceAccount and how is it used?

**Answer:**
A **ServiceAccount** provides an identity for processes running in a Pod . When processes in a Pod need to authenticate to the Kubernetes API, they use a ServiceAccount.

**Key concepts**:
- Each namespace has a `default` ServiceAccount
- ServiceAccounts can be granted permissions via RBAC
- Pods specify which ServiceAccount to use
- The associated token is mounted at `/var/run/secrets/kubernetes.io/serviceaccount/token`

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-app-sa
  namespace: default
```

**Using in a Pod**:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  serviceAccountName: my-app-sa
  containers:
  - name: app
    image: myapp:latest
```

**Common use cases**:
- Giving Pods permissions to access Kubernetes API
- Pulling images from private registries (via imagePullSecrets)
- Identifying workloads for security policies

### Q24: What are Roles and ClusterRoles?

**Answer:**
**Roles** and **ClusterRoles** define sets of permissions (rules) in Kubernetes' RBAC system .

| Aspect | Role | ClusterRole |
|--------|------|-------------|
| **Scope** | Namespace-specific | Cluster-wide (all namespaces) |
| **Resources** | Namespaced resources (Pods, Services) | Namespaced + cluster resources (Nodes, PVs) |
| **Use cases** | Team permissions in a namespace | Admin permissions, cross-namespace access |

**Role example** (namespace-scoped):
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get", "list"]
```

**ClusterRole example** (cluster-wide):
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-reader
rules:
- apiGroups: [""]
  resources: ["nodes"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["persistentvolumes"]
  verbs: ["get", "list"]
```

### Q25: What are RoleBindings and ClusterRoleBindings?

**Answer:**
**RoleBindings** and **ClusterRoleBindings** grant the permissions defined in Roles/ClusterRoles to subjects (users, groups, or ServiceAccounts) .

| Binding Type | References | Grants permissions to |
|--------------|------------|----------------------|
| **RoleBinding** | Role (same namespace) | Subjects in same namespace |
| **RoleBinding** | ClusterRole (cluster-wide) | Subjects in its namespace (subset of ClusterRole) |
| **ClusterRoleBinding** | ClusterRole | Subjects cluster-wide |

**RoleBinding example** (binding local Role):
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default
subjects:
- kind: User
  name: jane
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**RoleBinding with ClusterRole** (recommended for reusability):
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default
subjects:
- kind: ServiceAccount
  name: my-app-sa
  namespace: default
roleRef:
  kind: ClusterRole
  name: view  # Built-in view ClusterRole
  apiGroup: rbac.authorization.k8s.io
```

### Q26: What are PodSecurityPolicies (deprecated) and PodSecurity Standards?

**Answer:**
**PodSecurityPolicies (PSP)** were a built-in admission controller that controlled security-sensitive aspects of Pod specification . They were **deprecated in v1.21 and removed in v1.25** due to complexity.

**Current approach: Pod Security Standards (PSS) and Pod Security Admission (PSA)**:

**Pod Security Standards** define three policy levels:

| Level | Description | Use Case |
|-------|-------------|----------|
| **Privileged** | Unrestricted policy | System-level workloads |
| **Baseline** | Minimally restrictive, prevents known privilege escalations | Most applications |
| **Restricted** | Heavily restricted, follows Pod hardening best practices | Security-critical apps |

**Enforcement modes**:
- **enforce**: Violations cause Pod rejection
- **audit**: Violations recorded in audit logs
- **warn**: Violations show warnings to users

**Label-based enforcement**:
```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: my-namespace
  labels:
    pod-security.kubernetes.io/enforce: baseline
    pod-security.kubernetes.io/enforce-version: latest
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
```

## Scenario-Based Questions

### Q27: You need to deploy a database that requires persistent storage and stable network identity. Which object would you use?

**Answer:**
Use a **StatefulSet** with a Service and PersistentVolumeClaims.

**Why StatefulSet**:
- **Stable network identity**: Pods get predictable names (db-0, db-1, db-2)
- **Stable storage**: Each replica gets its own persistent volume that persists across rescheduling
- **Ordered deployment**: Essential for databases that need primary/replica setup

**Example configuration**:
```yaml
apiVersion: v1
kind: Service
metadata:
  name: mysql
spec:
  clusterIP: None  # Headless service for stable DNS
  selector:
    app: mysql
  ports:
  - port: 3306
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql
  replicas: 3
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        env:
        - name: MYSQL_ROOT_PASSWORD
          valueFrom:
            secretKeyRef:
              name: mysql-secret
              key: root-password
        volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 10Gi
```

### Q28: How would you expose a set of Pods internally to other services in the same namespace?

**Answer:**
Use a **ClusterIP Service** (the default type).

```yaml
apiVersion: v1
kind: Service
metadata:
  name: backend-service
spec:
  selector:
    app: backend
    tier: api
  ports:
  - port: 8080
    targetPort: 8080
    protocol: TCP
```

**How other Pods access it**:
- By service name: `backend-service`
- By service name with namespace: `backend-service.default.svc.cluster.local`

**Why ClusterIP is appropriate**:
- Only needs internal cluster access
- No external exposure required
- Provides load balancing and service discovery
- Most secure (no external entry points)

### Q29: You need to expose multiple HTTP services externally with a single load balancer. What would you use?

**Answer:**
Use an **Ingress** resource with an Ingress Controller.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: main-ingress
spec:
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /users
        pathType: Prefix
        backend:
          service:
            name: user-service
            port:
              number: 80
      - path: /orders
        pathType: Prefix
        backend:
          service:
            name: order-service
            port:
              number: 80
  - host: app.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-service
            port:
              number: 80
  tls:
  - hosts:
    - api.example.com
    - app.example.com
    secretName: wildcard-tls
```

**Benefits**:
- Single external load balancer (cost-effective)
- Host and path-based routing
- TLS termination at Ingress level
- Centralized configuration

### Q30: How would you restrict which Pods can communicate with your database?

**Answer:**
Use a **NetworkPolicy** to restrict ingress traffic to the database Pods.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: database-network-policy
spec:
  podSelector:
    matchLabels:
      app: database
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          role: backend
    ports:
    - protocol: TCP
      port: 5432
```

**Additional restrictions**:
```yaml
# Restrict to specific namespaces
  - from:
    - namespaceSelector:
        matchLabels:
          environment: production
      podSelector:
        matchLabels:
          app: api
```

**Important**: NetworkPolicy requires a CNI that supports it (Calico, Cilium, Weave).

### Q31: You need to run a batch job every night at 2 AM. Which object do you use?

**Answer:**
Use a **CronJob** to schedule the job.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 2 * * *"  # Cron syntax: at 2 AM daily
  concurrencyPolicy: Forbid  # Don't run if previous still running
  startingDeadlineSeconds: 300  # Must start within 5 minutes
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup
            image: backup-tool:latest
            command:
            - /bin/sh
            - -c
            - |
              /usr/bin/backup-script
              /usr/bin/upload-to-s3
          restartPolicy: OnFailure
```

**CronJob features**:
- **schedule**: Standard cron syntax
- **concurrencyPolicy**: Allow/Forbid/Replace concurrent runs
- **startingDeadlineSeconds**: How late can a job start
- **successfulJobsHistoryLimit**: How many completed jobs to keep

### Q32: Your application needs to read the Kubernetes API to discover other services. How do you grant permissions?

**Answer:**
Use a **ServiceAccount** with appropriate **RBAC** permissions.

**Step 1: Create ServiceAccount**:
```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: api-client
  namespace: default
```

**Step 2: Create Role with necessary permissions**:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: service-reader
rules:
- apiGroups: [""]
  resources: ["services"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["endpoints"]
  verbs: ["get", "list"]
```

**Step 3: Bind Role to ServiceAccount**:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-services
  namespace: default
subjects:
- kind: ServiceAccount
  name: api-client
  namespace: default
roleRef:
  kind: Role
  name: service-reader
  apiGroup: rbac.authorization.k8s.io
```

**Step 4: Use in Pod**:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: api-client-pod
spec:
  serviceAccountName: api-client
  containers:
  - name: app
    image: myapp:latest
```

The Pod will have a mounted token at `/var/run/secrets/kubernetes.io/serviceaccount/token` that it can use to authenticate to the API server.

### Q33: You need to ensure that Pods in your namespace don't consume too many resources and have default resource limits. What do you create?

**Answer:**
Create both a **LimitRange** (for per-Pod limits) and a **ResourceQuota** (for total namespace limits).

**LimitRange** (per-Pod defaults and limits):
```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: resource-limits
  namespace: myapp
spec:
  limits:
  - max:
      cpu: "2"
      memory: 4Gi
    min:
      cpu: "100m"
      memory: 256Mi
    default:
      cpu: "500m"
      memory: 1Gi
    defaultRequest:
      cpu: "200m"
      memory: 512Mi
    type: Container
```

**ResourceQuota** (total namespace resources):
```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-quota
  namespace: myapp
spec:
  hard:
    requests.cpu: "8"
    requests.memory: 16Gi
    limits.cpu: "16"
    limits.memory: 32Gi
    pods: "20"
```

**Together they provide**:
- **Protection from greedy pods**: Any single Pod can't take all resources
- **Protection from namespace overload**: Total resources limited
- **Good defaults**: Users can omit resource spec and still get reasonable limits
- **Fair sharing**: Multiple applications can coexist safely

### Q34: How do you ensure your Deployment rolls out updates without downtime?

**Answer:**
Configure the Deployment with a **RollingUpdate strategy** and appropriate **health probes**.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # Can create 1 extra pod above desired count
      maxUnavailable: 0  # Must keep all pods available during update
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
        ports:
        - containerPort: 80
        readinessProbe:
          httpGet:
            path: /healthz
            port: 80
          initialDelaySeconds: 5
          periodSeconds: 5
        livenessProbe:
          httpGet:
            path: /healthz
            port: 80
          initialDelaySeconds: 15
          periodSeconds: 20
```

**Why this works**:
- **maxSurge: 1**: One new Pod can be created before old ones are removed
- **maxUnavailable: 0**: Always keep all 5 replicas available
- **readinessProbe**: Only healthy Pods receive traffic
- **livenessProbe**: Kubernetes restarts unhealthy Pods

**During update**:
1. New Pod created (now 6 total)
2. When new Pod is ready, one old Pod terminated (back to 5)
3. Process repeats until all are updated

5. **Practice with YAML** - Be comfortable reading and writing object specifications

6. **Know when to use each object** - Scenario-based questions test your understanding of object purposes

7. **Understand object interactions** - How Services connect to Pods, how PVCs bind to PVs, how Roles bind to ServiceAccounts
