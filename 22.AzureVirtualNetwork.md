# Azure Virtual Network interview questions


## Part 1: Basic to Intermediate Level

### 1. What is an Azure Virtual Network (VNet) and what are its core components?
**Answer:**
An Azure Virtual Network (VNet) is the fundamental building block for your private network in Azure. It enables many types of Azure resources, such as Azure Virtual Machines (VMs), to securely communicate with each other, the internet, and on-premises networks. A VNet is similar to a traditional network that you'd operate in your own data center but brings with it additional benefits of Azure's infrastructure such as scale, availability, and isolation .

**Core Components:**
- **Address Space:** One or more private IP address ranges (in CIDR notation, e.g., 10.0.0.0/16) that are assigned to the VNet. These addresses are not internet-routable.
- **Subnets:** Segments of the VNet's address space that allow you to partition the network into smaller, logical networks. This helps in organizing and securing resources based on their function (e.g., web tier, application tier, database tier) .
- **Network Interface Card (NIC):** The interconnection point between a VM and a VNet. A VM must have at least one NIC attached to it, which is assigned a private IP address from the subnet it's connected to .

### 2. What is the difference between a Public IP Address and a Private IP Address?
**Answer:**
- **Private IP Addresses:** These are used for communication *within* an Azure VNet and between resources in the same VNet or peered VNets. They are not routable over the internet. Resources like VMs, Internal Load Balancers, and Application Gateways use private IPs .
- **Public IP Addresses:** These are used for communication *from the internet* to Azure resources (inbound) and from Azure resources to the internet (outbound). A public IP address can be assigned directly to a resource like a VM's NIC, or to a frontend configuration of a service like Azure Load Balancer, Application Gateway, or NAT Gateway . A key distinction is that a dynamic public IP address changes when a VM is stopped (deallocated) and restarted .

### 3. How do you secure traffic within a VNet using Network Security Groups (NSGs)?
**Answer:**
Network Security Groups (NSGs) are a fundamental tool for securing network traffic in Azure. An NSG acts as a stateful firewall that filters traffic at the **Layer 3 and Layer 4** (network and transport) levels. It contains a list of security rules that allow or deny inbound or outbound traffic .

- **Application:** An NSG can be associated with a **subnet** or a **network interface (NIC)**. When associated with a subnet, the rules apply to all resources within that subnet. When associated with a NIC, the rules apply only to that specific VM .
- **Rule Evaluation:** Rules are processed in priority order, from lowest to highest (e.g., priority 100 is processed before priority 200). Once a match is found, processing stops. Azure has default rules that allow traffic within a VNet and outbound to the internet, but these can be overridden by custom, higher-priority rules .
- **Use Case Example:** For a multi-tier application, you could create an NSG for the web subnet allowing inbound traffic only on port 443 (HTTPS) from the internet, and another NSG for the database subnet allowing inbound traffic only on port 1433 (SQL) from the web subnet's IP range .

### 4. What is an Application Security Group (ASG) and how does it simplify security management?
**Answer:**
An Application Security Group (ASG) enables you to group virtual machines logically by their workload or function (e.g., "WebServers," "AppServers," "DBServers") and define network security policies based on those groups . Instead of manually maintaining complex NSG rules with explicit source and destination IP addresses, you can use ASGs as sources or destinations in your NSG rules .

- **How it works:** You create an ASG, assign VMs to it, and then create an NSG rule that references the ASG. For example, an NSG rule could state: "Allow traffic from the 'WebServers' ASG to the 'AppServers' ASG on port 8080." If you add a new VM to the 'WebServers' ASG, it automatically inherits the associated network policies without any changes to the NSG rules .

### 5. What is a User-Defined Route (UDR) and when is it necessary?
**Answer:**
By default, Azure automatically creates a route table for each subnet within a VNet, which handles routing between subnets, to on-premises networks via VPN/ExpressRoute, and to the internet. A **User-Defined Route (UDR)** allows you to override Azure's default system routes or add more specific routes to control the path that network traffic takes .

- **When is it necessary?** UDRs are essential when you want to force traffic to go through a **Network Virtual Appliance (NVA)** or a firewall like Azure Firewall for inspection. For example, if you have a firewall in a central subnet and you want all traffic from other subnets to the internet to be inspected, you would create a UDR on those subnets with a destination of `0.0.0.0/0` (internet) and a next hop set to the private IP address of the firewall . This is a key component of a hub-and-spoke topology .

### 6. What is Azure NAT Gateway and what problem does it solve?
**Answer:**
Azure NAT Gateway is a fully managed and highly resilient service that simplifies outbound-only Internet connectivity for virtual networks . It solves the problem of managing outbound connectivity for resources with private IPs.

- **How it works:** You associate a NAT Gateway with a public IP address or a public IP prefix and then attach it to one or more subnets within a VNet. Any virtual machine or resource in those subnets will then use the NAT Gateway's public IP address(es) for all outbound internet traffic .
- **Key Benefits:**
    - **Secure Outbound Connection:** Resources inside the VNet remain private (no need for public IPs on individual VMs), while they can still access the internet for updates, patches, or calling external APIs.
    - **Static Outbound IP:** Provides a consistent set of public IP addresses for outbound traffic, which is crucial for whitelisting scenarios with external partners .
    - **Performance and Scalability:** Supports up to 64,000 concurrent flows per public IP and scales automatically without requiring manual configuration.

### 7. What is Azure Bastion and why would you use it instead of a Jumpbox VM?
**Answer:**
Azure Bastion is a fully managed Platform-as-a-Service (PaaS) offering that provides secure and seamless Remote Desktop Protocol (RDP) and Secure Shell (SSH) access to virtual machines directly through the Azure portal, over SSL . It eliminates the need to assign public IP addresses to VMs for management access.

- **Why use Azure Bastion over a Jumpbox?**
    - **Security:** A traditional jumpbox is a VM that you must manage, patch, and secure. It often has its own public IP, creating an additional attack surface. Azure Bastion is managed by Microsoft, hardened against attacks, and provides RDP/SSH access without exposing any public endpoint on your VMs .
    - **Simplicity:** It provides a seamless, browser-based experience. You can connect to your VMs directly from the Azure portal without installing any extra client software.
    - **Protection against Port Scanning:** Since VMs don't have public IPs, they are not discoverable from the internet, effectively protecting them from port scanning and other external attacks .

### 8. What is Azure Private Link and Azure Private Endpoint?
**Answer:**
**Azure Private Link** is a service that enables you to access Azure PaaS Services (like Azure Storage, SQL Database, or Azure Key Vault) and services hosted by other Azure customers or partners over a **private endpoint** in your virtual network. This ensures that traffic between your VNet and the service traverses entirely over the Microsoft backbone network, eliminating exposure to the public internet .

- **Azure Private Endpoint** is the network interface that connects you privately and securely to a service powered by Azure Private Link. It assigns a **private IP address** from your VNet to the PaaS service .
- **Scenario:** You need to secure access to an Azure SQL Database from your VNet without allowing public internet access. You would create a Private Endpoint for the SQL Database in your VNet. Your application then connects to the database using the private IP, and traffic never leaves the Azure network. This also prevents data exfiltration risks .

## Part 2: Advanced Level

### 9. Describe a hub-and-spoke network topology and its key components.
**Answer:**
Hub-and-spoke is a networking model for managing large-scale, complex environments in Azure. It helps centralize common services (like connectivity and security) while allowing workloads to be isolated and managed independently .

- **Hub VNet:** The central VNet that acts as a connectivity point. It typically contains shared services that are consumed by all workloads, such as:
    - **Azure Firewall** or a third-party NVA for inspecting traffic.
    - **VPN Gateway** or **ExpressRoute Gateway** for hybrid connectivity to on-premises networks.
    - **Azure Bastion** for secure management access.
    - **Azure DNS** for name resolution.
- **Spoke VNets:** Individual VNets that host specific workloads or applications (e.g., Production VNet, Development VNet, a VNet for a specific business unit). Spokes are isolated from each other but can connect to the hub to access the shared services .
- **Connectivity:** VNet Peering is used to connect the hub to each spoke. UDRs are configured in the spokes to force traffic through the hub firewall for inspection . The hub-and-spoke model improves manageability, security, and cost efficiency.

### 10. How would you force all traffic between two spoke VNets to go through a firewall in the hub VNet?
**Answer:**
This is a common requirement in a hub-and-spoke topology. By default, VNet Peering allows direct communication between peered VNets. To force traffic through the hub firewall, you must disable that default behavior and use UDRs.

**Steps:**
1.  **Deploy Firewall:** Deploy an Azure Firewall (or NVA) in the hub VNet and note its private IP address.
2.  **Configure VNet Peering:** Establish VNet peerings between the hub and each spoke. In the peering configuration for **each spoke VNet**, set the **"Use the remote virtual network's gateway or Route Server"** setting to **Disabled**. More importantly, ensure **"Allow forwarded traffic"** is **Enabled** on the hub's peering connection to accept traffic routed by the UDR .
3.  **Create UDRs:** For each subnet in the spoke VNets that needs to communicate with another spoke, create a route table and associate it with the subnet.
    - Add a custom route (UDR) with a destination that covers the IP address space of the *other* spoke VNet (e.g., 10.2.0.0/16).
    - Set the **Next hop type** to **Virtual appliance**.
    - Set the **Next hop address** to the private IP address of the firewall in the hub (e.g., 10.0.1.4) .

With this configuration, traffic from Spoke A destined for Spoke B will match the UDR and be sent to the firewall. The firewall, with "Allow forwarded traffic" enabled on the peering, can then inspect the traffic and route it to Spoke B.

### 11. Explain Azure Route Server and its role in dynamic routing.
**Answer:**
Azure Route Server is a fully managed service that simplifies dynamic routing between Network Virtual Appliances (NVAs) and your virtual network . It allows your NVAs (like firewalls or SD-WAN appliances) to exchange routes with Azure's software-defined network (SDN) using the Border Gateway Protocol (BGP).

- **How it works:** You deploy Azure Route Server into a dedicated subnet in your hub VNet. You then establish BGP peering sessions between your NVAs and the Route Server. The Route Server learns routes from the NVAs and automatically programs them into the route tables of all VMs in the VNet (and peered VNets) .
- **Key Benefits:**
    - **Simplified Management:** Eliminates the need to manually configure UDRs on every subnet for routes learned from on-premises or other NVAs.
    - **Dynamic Updates:** If an NVA learns a new route or a route is withdrawn, it updates the Route Server via BGP, and Azure automatically updates the effective routes for all VMs.
    - **High Availability:** The service is designed with zone-level redundancy .
- **Use Case:** An SD-WAN NVA deployed in Azure can peer with Azure Route Server. The NVA can advertise specific on-premises network prefixes to Route Server, which then ensures all VMs in the connected VNets know how to reach those on-premises locations without manual UDRs.

### 12. What is the difference between Service Endpoints and Private Endpoints? When would you choose one over the other?
**Answer:**
Both Service Endpoints and Private Endpoints secure access to Azure PaaS services, but they work in fundamentally different ways .

| Feature | Service Endpoints | Private Endpoints |
| :--- | :--- | :--- |
| **Connectivity** | Extends your VNet's private address space and identity to the PaaS service over the Azure backbone. | Provides a private IP address from your VNet to the PaaS service. |
| **Service Accessibility** | The PaaS service still has a **public endpoint**. Access is secured by allowing your VNet's traffic to that public endpoint via firewall rules. | The PaaS service is brought **into your VNet**. It effectively has no public endpoint, or it can be disabled. |
| **Target Resource** | The PaaS service resource itself (e.g., the Storage Account). | A network interface (Private Endpoint) connected to the PaaS service. |
| **Traffic Path** | Traffic still uses the public endpoint's IP address, but the route is optimized and secured via the Microsoft backbone. | Traffic uses the private IP address and stays entirely within your VNet and the Microsoft backbone. |
| **Cost** | Free (included). | Incurs a small hourly charge. |

**When to choose which?**
- **Choose Service Endpoints** if you need a cost-effective way to secure access from within your VNet to multiple PaaS services and you don't need to eliminate the public endpoint entirely.
- **Choose Private Endpoints** for a defense-in-depth strategy, to completely remove data exfiltration risks, for hybrid scenarios where on-premises needs private access, or when compliance requires a completely private connection . For example, for a production Azure SQL Database, you would almost always choose a Private Endpoint .

### 13. How would you troubleshoot a scenario where a user cannot connect to a VM via Azure Bastion?
**Answer:**
When a user receives an error like "Your session has ended" or "Unable to connect" via Azure Bastion, follow this systematic troubleshooting approach :

1.  **Verify Bastion Deployment and Health:** Ensure Azure Bastion is deployed in the same VNet as the target VM. Check its resource health in the Azure portal to confirm it's running and healthy .
2.  **Check NSG Rules:** The most common cause is restrictive NSG rules.
    - The subnet where Bastion is deployed needs inbound/outbound rules for HTTPS (TCP 443) for management.
    - The target VM's subnet (or its NIC) needs inbound rules allowing traffic from the Bastion subnet on RDP (TCP 3389) or SSH (TCP 22) .
3.  **Verify VM Status and OS:** Confirm the target VM is in a "Running" state. The VM's guest OS must also be running and have the RDP or SSH service enabled.
4.  **Check User Permissions (RBAC):** The user must have the correct RBAC roles to use Bastion. At a minimum, they need **Reader** role on the VM. To actually connect, they also need either the **Virtual Machine User Login** role (for non-admin access) or **Virtual Machine Administrator Login** role (for admin access) .
5.  **Browser/Client Issues:** If using the browser, try a different browser or clear the cache/cookies. If using the native client, ensure the feature is enabled in the Bastion Standard SKU.
6.  **Restart Bastion:** As a last resort, restarting the Bastion resource can resolve transient service issues .

### 14. Explain the role of custom DNS and Azure DNS Private Resolver in a hybrid environment.
**Answer:**
By default, Azure provides internal DNS for name resolution within a VNet. However, in hybrid scenarios where on-premises and Azure resources need to resolve each other's names, you need a custom DNS solution.

- **Custom DNS Servers:** You can configure your VNet to use custom DNS servers (e.g., on-premises Domain Controllers). This allows VMs in Azure to resolve on-premises hostnames. To enable on-premises to resolve Azure private IPs, you typically need to configure conditional forwarders on your on-premises DNS servers to forward requests for a specific domain (e.g., `internal.cloudapp.net` or your private zone) to Azure.
- **Azure DNS Private Resolver:** This is a fully managed Azure service that provides a more elegant solution for hybrid DNS resolution. It allows you to resolve on-premises DNS domains from Azure and *vice versa* without having to deploy and manage VMs as DNS servers. It can perform conditional forwarding between on-premises and Azure, bridging the two DNS environments securely over ExpressRoute or VPN .

### 15. What are the key differences between Azure Load Balancer and Azure Application Gateway?
**Answer:**
While both distribute traffic, they operate at different layers of the OSI model and serve different purposes .

| Feature | Azure Load Balancer | Azure Application Gateway |
| :--- | :--- | :--- |
| **OSI Layer** | Layer 4 (Transport) - TCP/UDP | Layer 7 (Application) - HTTP/HTTPS |
| **Traffic Type** | Any TCP/UDP traffic. | Web traffic (HTTP, HTTPS). |
| **Key Features** | High throughput, low latency, supports any protocol. | SSL termination, Web Application Firewall (WAF), cookie-based session affinity, URL path-based routing, redirection. |
| **Use Case** | Load balancing traffic to a pool of VMs for non-HTTP workloads like SQL AlwaysOn, RDP, or internal APIs . | Load balancing web applications where you need advanced routing, security (WAF), or offloading SSL . |
