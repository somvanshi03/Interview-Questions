# Azure Kubernetes Service (AKS) interview questions


## Part 1: Basic to Intermediate Level

### 1. What is Azure Kubernetes Service (AKS) and how does it simplify container management?
**Answer:**
Azure Kubernetes Service (AKS) is a managed container orchestration service provided by Microsoft Azure that simplifies deploying, managing, and scaling containerized applications using Kubernetes . It eliminates the complexity of manual Kubernetes management by offloading the operational overhead to Azure .

**Key simplifications include:**
- **Managed Control Plane:** Azure manages the Kubernetes master nodes (control plane) including the API server, etcd, and scheduler, allowing development teams to focus on building applications rather than infrastructure .
- **Automated Upgrades and Patching:** Azure handles version upgrades, security patches, and health monitoring of the control plane .
- **Integrated Experience:** AKS integrates seamlessly with Azure services like Azure Active Directory for authentication, Azure Monitor for logging, and Azure Container Registry (ACR) for image storage .

### 2. Explain the architecture of an AKS cluster, including the relationship between clusters, nodes, pods, and containers.
**Answer:**
The architecture of an AKS cluster follows a hierarchical structure :

- **Cluster:** The top-level representation of the Kubernetes infrastructure. It provides the logical representation of the underlying infrastructure and manages the deployment and scaling of containerized applications .
- **Nodes:** Worker machines (virtual machines) that run containerized applications. Each node runs a kubelet (agent that communicates with the control plane), kube-proxy (for networking), and a container runtime (like containerd) . Nodes can be grouped into **node pools** for managing different workloads with specific VM sizes and configurations .
- **Pods:** The smallest and most basic deployable unit in Kubernetes. A pod represents a single instance of a running process and can contain one or more containers that share the same network namespace and can communicate via localhost .
- **Containers:** Lightweight, standalone executable packages that include code, runtime, system tools, and libraries. Within a pod, multiple containers can run different processes that work together .

### 3. What networking models does AKS support, and how do they differ?
**Answer:**
AKS supports two primary network models :

**1. Azure CNI (Container Networking Interface):**
- Each pod receives an IP address directly from the Azure Virtual Network (VNet) subnet.
- Pods can communicate directly with other resources in the VNet, making it suitable for scenarios requiring advanced networking features like Network Security Groups (NSGs) and User-Defined Routes (UDRs).
- Requires more IP addresses from the VNet, so proper planning of IP space is essential.

**2. Kubenet (Basic Networking):**
- Pods receive internal IP addresses from a private CIDR range.
- Nodes use Network Address Translation (NAT) to communicate outside the node.
- Conserves IP addresses from the VNet, making it suitable for simpler networking needs or when IP space is limited.
- Typically requires less configuration but has limitations compared to Azure CNI.

### 4. How does service exposure work in AKS? Describe the different service types.
**Answer:**
Kubernetes services define a logical set of pods and a policy for accessing them. AKS supports several service types :

- **ClusterIP (Default):** Exposes the service on an internal IP address within the cluster. Only accessible from within the cluster, used for internal communication between microservices.
- **NodePort:** Exposes the service on a static port on each node's IP address. Accessible from outside the cluster by connecting to `<NodeIP>:<NodePort>`. Useful for development and testing.
- **LoadBalancer:** Exposes the service externally using Azure's load balancer. When created, AKS automatically provisions and configures an Azure Load Balancer. This is the standard way to expose production workloads to the internet.
- **ExternalName:** Maps a service to a DNS name (CNAME record) rather than a selector. Used to proxy requests to external services outside the Kubernetes cluster.

### 5. What are node pools, and why would you use multiple node pools?
**Answer:**
Node pools are groups of nodes within an AKS cluster that share the same configuration, including VM size, operating system, and scaling policies .

**Use cases for multiple node pools :**
- **Workload Diversity:** Run different types of workloads on appropriately sized VMs (e.g., memory-optimized VMs for databases, GPU-enabled VMs for machine learning).
- **Cost Optimization:** Use spot node pools for non-critical, fault-tolerant workloads to reduce costs.
- **Isolation:** Separate system workloads (like ingress controllers or monitoring agents) from application workloads to ensure critical system components have dedicated resources.
- **Compliance:** Isolate workloads with specific compliance requirements from general-purpose workloads.

## Part 2: Advanced Level

### 6. How do you implement authentication and authorization in AKS, and what is the role of Azure AD integration?
**Answer:**
AKS provides robust identity and access management through integration with Azure Active Directory (AAD) and Kubernetes RBAC .

**Azure AD Integration :**
- AAD serves as the identity provider for cluster authentication.
- Users and groups authenticate using their AAD credentials to access the Kubernetes API server via `kubectl` or other tools.
- This eliminates the need to manage separate Kubernetes user accounts and enables centralized identity management.

**Kubernetes RBAC :**
- RBAC controls what authenticated users can do within the cluster by defining roles and role bindings.
- **Roles:** Define permissions (verbs like `get`, `list`, `create`, `delete`) on resources (like `pods`, `deployments`).
- **RoleBindings:** Assign roles to users, groups, or service accounts.
- **ClusterRoles/RoleBindings:** Similar but apply across the entire cluster (not limited to a namespace).

**Example RBAC configuration :**
```yaml
# Role allowing read access to pods in the default namespace
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "watch", "list"]

# Binding assigning the role to an AAD user
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default
subjects:
- kind: User
  name: "user@contoso.com"  # AAD user principal name
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

### 7. Describe the scaling options available in AKS and when to use each.
**Answer:**
AKS offers multiple scaling mechanisms to handle varying workload demands :

**1. Horizontal Pod Autoscaler (HPA) :**
- Automatically scales the number of pod replicas based on observed metrics like CPU utilization, memory usage, or custom metrics.
- **Use Case:** Web applications with variable traffic patterns (e.g., e-commerce sites that scale during peak shopping hours).
- **Example command:**
  ```bash
  kubectl autoscale deployment myapp --cpu-percent=70 --min=3 --max=10
  ```

**2. Cluster Autoscaler :**
- Automatically adjusts the number of nodes in the cluster based on pending pod requirements.
- When pods can't be scheduled due to insufficient resources, the cluster autoscaler provisions additional nodes; when nodes are underutilized, it removes them.
- **Use Case:** Environments with unpredictable workloads where manual node management is impractical.
- **Example CLI:**
  ```bash
  az aks update --resource-group myRG --name myAKSCluster --enable-cluster-autoscaler --min-count 1 --max-count 10
  ```

**3. Manual Scaling :**
- Direct control over pod replica counts or node counts through `kubectl scale` or `az aks scale` commands.
- **Use Case:** Predictable workloads, maintenance windows, or when autoscaling is not appropriate.

### 8. How would you design and implement a CI/CD pipeline for deploying applications to AKS using Azure DevOps?
**Answer:**
A comprehensive CI/CD pipeline for AKS typically includes build, containerization, and deployment stages :

**Pipeline Stages :**

**1. Build and Containerize Stage:**
- Agent: Microsoft-hosted (e.g., `ubuntu-latest`).
- **Steps:**
  - Restore dependencies (`dotnet restore`, `npm install`, etc.).
  - Build and test the application.
  - Publish artifacts.
  - Build Docker image and tag with build ID (`myacr.azurecr.io/app:$(Build.BuildId)`).
  - Push image to Azure Container Registry (ACR) using a configured service connection.
  - Publish Kubernetes manifests (Helm charts or YAML files) as pipeline artifacts.

**2. Deploy to Development Environment:**
- **Steps:**
  - Use `Kubernetes@1` or `Helm@3` task to deploy to Dev AKS cluster.
  - Set image tag dynamically (`--set image.tag=$(Build.BuildId)`).
  - Run smoke tests to verify deployment (e.g., `curl <dev-endpoint>/health`).

**3. Deploy to Staging Environment:**
- **Pre-deployment:** Manual approval gate.
- **Steps:**
  - Deploy to staging AKS cluster/namespace.
  - Run comprehensive integration and end-to-end tests.

**4. Deploy to Production Environment:**
- **Pre-deployment:** Strict manual approval process with higher-level approvers.
- **Steps:**
  - Deploy using advanced strategies like blue-green or canary deployments.
  - Consider traffic splitting via service mesh or ingress controller.

**Infrastructure as Code Integration :**
- Use Terraform in the pipeline for infrastructure provisioning:
  - `terraform init` - Initialize backend.
  - `terraform validate` - Check configuration.
  - `terraform plan -out=tfplan` - Generate execution plan.
  - `terraform apply tfplan` - Apply changes (with approval gates).

### 9. What are the best practices for securing an AKS cluster in a production environment?
**Answer:**
Securing an AKS cluster requires a defense-in-depth approach across multiple layers :

**1. Authentication and Authorization :**
- Integrate with Azure AD for identity management.
- Implement Kubernetes RBAC with least privilege principle.
- Use Azure RBAC for controlling access to Azure resources.

**2. Network Security :**
- Implement Network Policies to control pod-to-pod communication.
- Use NSGs to restrict access to cluster subnets.
- Consider Azure Firewall for egress traffic control.
- Enable Azure CNI for advanced network security features.

**3. Secrets Management :**
- Store sensitive information in Kubernetes Secrets.
- Integrate with Azure Key Vault using the Secrets Store CSI driver.
- Never hardcode secrets in manifests or container images.

**4. Pod Security :**
- Implement Pod Security Standards (baseline/restricted).
- Use security contexts to control privilege escalation.
- Avoid running containers as root.
- Use read-only root filesystems where possible.

**5. Image Security :**
- Use trusted, minimal base images.
- Regularly scan images for vulnerabilities (using Azure Security Center or ACR tasks).
- Sign and verify images.

**6. Monitoring and Threat Detection :**
- Enable Azure Monitor for containers.
- Use Microsoft Defender for Cloud for threat detection.
- Enable audit logging for the Kubernetes API server.

**7. Regular Updates :**
- Keep Kubernetes version updated with security patches.
- Regularly update node images.
- Have a patch management strategy.

### 10. How would you approach disaster recovery for AKS workloads?
**Answer:**
A comprehensive disaster recovery strategy for AKS involves multiple components and approaches :

**1. Multi-Region Deployment :**
- Deploy AKS clusters in geographically redundant Azure regions.
- Use Azure Traffic Manager to distribute traffic and enable automatic failover.
- Design for active-passive or active-active patterns based on recovery objectives.

**2. Data Backup and Replication :**
- **Velero (formerly Heptio Ark):** Back up Kubernetes resources and persistent volumes.
  - Schedule regular backups of cluster state (deployments, services, ConfigMaps).
  - Store backups in Azure Blob Storage with geo-redundancy.
- **Persistent Volume Snapshots:** Use Azure Disk Snapshots for point-in-time copies of persistent data.
- **Database Replication:** For stateful workloads, configure database replication across regions (e.g., Azure SQL Geo-Replication, Cosmos DB multi-region writes).

**3. Infrastructure as Code (IaC) :**
- Define cluster configuration and workloads using Terraform or ARM templates.
- Store IaC in version control to enable quick recreation of environments.
- Example Terraform backend configuration:
  ```hcl
  terraform {
    backend "azurerm" {
      resource_group_name  = "tfstate-rg"
      storage_account_name = "mystatestorageaccount"
      container_name       = "tfstate"
      key                  = "prod-aks.tfstate"
    }
  }
  ```

**4. Disaster Recovery Drills :**
- Regularly test failover procedures.
- Validate restore processes from backups.
- Document recovery steps and RTO/RPO expectations.

**5. Monitoring and Alerting :**
- Set up alerts for cluster health issues across regions.
- Monitor cross-region replication status.
- Use Azure Service Health to be notified of Azure outages.

### 11. Explain how Network Policies work in AKS and provide an example of restricting pod-to-pod communication.
**Answer:**
Network Policies are Kubernetes resources that control how pods communicate with each other and with other network endpoints. They act as a firewall for pods, implementing isolation and security at the IP address or port level .

**Requirements:**
- The AKS cluster must use a network policy engine (either Calico or Azure Network Policy).
- Network policies are namespace-scoped.

**Example Scenario:**
Restrict traffic so that only pods with label `app: frontend` can access pods with label `app: backend` on port 8080.

**NetworkPolicy YAML :**
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-policy
  namespace: default
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080
```

**Apply the policy:**
```bash
kubectl apply -f backend-policy.yaml
```

This policy ensures that only pods labeled `app: frontend` can communicate with backend pods on port 8080, providing network-level isolation between application tiers.

### 12. How do you integrate a service mesh (like Istio or Linkerd) with AKS, and what benefits does it provide?
**Answer:**
A service mesh provides a dedicated infrastructure layer for handling service-to-service communication, offloading concerns like traffic management, security, and observability from application code .

**Integration Steps for Istio :**
1. **Install Istio CLI:** Download and install the `istioctl` command-line tool.
2. **Install Istio on AKS:** Use `istioctl install` to deploy Istio control plane components.
3. **Label Namespace:** Add the label `istio-injection=enabled` to namespaces where you want automatic sidecar proxy injection.
4. **Deploy Applications:** When you deploy applications to labeled namespaces, Istio automatically injects Envoy sidecar proxies alongside your containers.
5. **Configure Traffic Rules:** Use Istio resources (VirtualServices, DestinationRules) to manage traffic routing, timeouts, retries, and canary deployments.

**Benefits of Service Mesh in AKS :**
- **Traffic Management:** Fine-grained control over traffic routing, including A/B testing, canary deployments, and blue-green deployments.
- **Security:** Automatic mTLS encryption between services, fine-grained access policies.
- **Observability:** Built-in metrics, distributed tracing, and service graphs without code changes.
- **Resilience:** Automatic retries, circuit breaking, and fault injection for testing.
- **Multi-Cluster Support:** Connect services across multiple AKS clusters.

### 13. Describe cost optimization strategies for running AKS clusters in production.
**Answer:**
Optimizing AKS costs requires a multi-faceted approach :

**1. Right-Sizing Resources :**
- Choose appropriate VM sizes for node pools based on workload requirements.
- Set resource requests and limits for pods to prevent resource waste.
- Use tools like Kubernetes Vertical Pod Autoscaler (VPA) to recommend optimal resource settings.

**2. Autoscaling :**
- Implement Horizontal Pod Autoscaler (HPA) to scale pods based on demand.
- Use Cluster Autoscaler to scale nodes up and down dynamically.
- Combine both to ensure resources match actual demand without overprovisioning.

**3. Spot Instances :**
- Use Azure Spot VMs for node pools running non-critical, fault-tolerant, or batch workloads.
- Spot instances offer significant discounts but can be evicted when Azure needs capacity.
- Design applications to handle eviction gracefully (e.g., using pod disruption budgets).

**4. Resource Quotas :**
- Set namespace-level resource quotas to prevent runaway workloads from consuming excessive resources.
- Example resource quota:
  ```yaml
  apiVersion: v1
  kind: ResourceQuota
  metadata:
    name: compute-quota
    namespace: dev
  spec:
    hard:
      requests.cpu: "10"
      requests.memory: 20Gi
      limits.cpu: "20"
      limits.memory: 40Gi
  ```

**5. Reserved Instances :**
- Purchase Azure Reserved VM Instances for baseline, predictable workloads.
- One-year or three-year commitments provide significant discounts compared to pay-as-you-go.

**6. Storage Optimization :**
- Use appropriate disk tiers (Premium SSD, Standard SSD, Standard HDD) based on performance requirements.
- Clean up unused disks and snapshots.
- Use Azure Files or Blob storage for shared storage needs.

**7. Monitoring and Cost Analysis :**
- Use Azure Cost Management + Billing to track spending.
- Enable Kubernetes cost monitoring with tools like Kubecost or Azure Advisor cost recommendations.
- Set budgets and alerts for unexpected spending.

### 14. How would you troubleshoot a pod that fails to mount a persistent volume in AKS?
**Answer:**
Troubleshooting persistent volume mounting issues requires systematic investigation :

**Step 1: Check Pod Status and Events**
```bash
# Get pod status
kubectl get pods

# Describe the pod for detailed events
kubectl describe pod <pod-name>
```
Look for events like "FailedMount," "VolumeBinding," or "MountVolume.SetUp failed."

**Step 2: Verify PersistentVolumeClaim (PVC) Status**
```bash
# Check PVC status (should be Bound)
kubectl get pvc

# Describe PVC for details
kubectl describe pvc <pvc-name>
```
A PVC stuck in "Pending" indicates the underlying PersistentVolume isn't available.

**Step 3: Check Storage Class Configuration**
```bash
# Verify storage class exists and is configured correctly
kubectl get storageclass
kubectl describe storageclass <storage-class-name>
```
Ensure the storage class references the correct Azure disk type and provisioninger.

**Step 4: Azure-Specific Checks**
- Verify the AKS cluster has the necessary permissions to create/manage disks in the resource group.
- Check if you've reached Azure disk limits (subscription or regional).
- Ensure the node's region/availability zone matches where the disk can be attached.

**Step 5: Check Node Disk Limits**
```bash
# Check node capacity and allocated resources
kubectl describe node <node-name>
```
Some VM sizes have limits on the number of data disks that can be attached.

**Step 6: Examine CSI Driver Logs (for Azure Disk CSI driver)**
```bash
# Find CSI driver pods
kubectl get pods -n kube-system | grep csi

# Check logs for errors
kubectl logs <csi-controller-pod> -n kube-system
```

**Common Issues and Solutions:**
- **PVC in Pending:** Storage class may be missing, or the disk can't be created (quota/permissions).
- **Multi-Attach Error:** A disk can only be attached to one node at a time in ReadWriteOnce mode.
- **Zone Mismatch:** The disk and node must be in the same availability zone.
- **Slow Provisioning:** Sometimes just waiting and retrying resolves transient Azure API issues.

### 15. How do you implement zero-downtime deployments in AKS, and what strategies are available?
**Answer:**
Zero-downtime deployments ensure application availability during updates. AKS supports several deployment strategies :

**1. Rolling Updates (Kubernetes Native)**
- The default strategy when updating deployments.
- Gradually replaces old pods with new ones.
- Configure `maxSurge` and `maxUnavailable` parameters to control the update pace.
- **Advantages:** Simple, no additional infrastructure required.
- **Limitations:** Both versions run simultaneously during transition; no traffic splitting control.

**2. Blue-Green Deployment **
- Maintain two identical environments (Blue = current, Green = new).
- Deploy the new version to the Green environment.
- Test thoroughly, then switch traffic from Blue to Green at the load balancer/ingress level.
- **Advantages:** Instant rollback by switching back to Blue; entire environment tested before cutover.
- **Implementation:** Use Kubernetes Services with selectors pointing to either Blue or Green deployment, update selector to switch.

**3. Canary Deployment **
- Gradually route a small percentage of traffic to the new version.
- Monitor metrics and errors; increase traffic percentage if all is well.
- **Advantages:** Real-world testing with production traffic; minimal blast radius.
- **Implementation:** Service mesh (Istio/Linkerd) or ingress controller with traffic splitting; multiple deployments with different replica counts.

**4. A/B Testing (similar to canary but for feature testing)**
- Route traffic based on headers, cookies, or user segments.
- Test specific features with targeted user groups.

**Prerequisites for Zero-Downtime :**
- **Readiness Probes:** Configure `readinessProbe` so Kubernetes knows when a pod is ready to receive traffic.
- **Pod Disruption Budgets:** Define `PodDisruptionBudget` to ensure minimum availability during voluntary disruptions.
- **Graceful Shutdown:** Applications should handle SIGTERM gracefully and complete in-flight requests.
- **Health Endpoints:** Implement `/health` and `/ready` endpoints.

**Example Readiness Probe:**
```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
```
